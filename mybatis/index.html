三条主线：

  1. 配置与映射构建：SqlSessionFactoryBuilder 把 mybatis-config.xml 与各个 XxxMapper.xml（或注解）解析成一张 Configuration——所有 MappedStatement、ResultMap、Cache、TypeHandler、插件都在这里登记；解析顺序（cache-ref 先于 cache、sql 先于 statements）与「不完整元素」延后补齐机制是这一阶段的两个关键设计（第一讲）。
  2. 执行器与缓存：openSession 装配出 CachingExecutor 装饰 Simple/Reuse/BatchExecutor 的链；一级缓存活在 BaseExecutor.localCache（会话级、默认开启），二级缓存活在 namespace 级 Cache（默认关闭、TransactionalCache 两阶段提交）（第二讲）。
  3. SQL 执行与映射：StatementHandler 家族负责 JDBC 语句生命周期，DefaultParameterHandler 负责 #{} → ? 绑定，DefaultResultSetHandler 负责 ResultSet → Java 对象（自动映射、嵌套映射/查询、鉴别器、延迟加载）；SqlSource（RawSqlSource/DynamicSqlSource）与 SqlNode 节点树负责”SQL 文本怎么来”（第三、四讲）。

#面试问题一句话结论深入
1MyBatis 的整体架构/工作原理？分三层：接口层（SqlSession + Mapper 动态代理）→ 核心处理层（Executor/StatementHandler/ParameterHandler/ResultSetHandler）→ 基础支撑层（Configuration/TypeHandler/日志/缓存）；一次调用 = 接口方法 → MappedStatement 查找 → Executor 链 → StatementHandler → JDBC → 结果映射第一、二讲
2#{} 和 ${} 的区别？#{} 在 SqlSource 生成期被 SqlSourceBuilder 换成 ? 占位符并记录 ParameterMapping，运行期由 TypeHandler 预编译绑定，无注入风险；${} 在运行期由 TextSqlNode 用 OGNL 求值后直接文本拼接，只能用于表名/列名等可信场景第四讲
3一级缓存是怎么回事？就是 BaseExecutor.localCache（PerpetualCache），会话级、默认开启且不可关闭；update 前必清（BaseExecutor.java:116），commit/rollback 前也清；queryStack + EXECUTION_PLACEHOLDER 防同一 key 递归查询第二讲
4一级缓存默认作用域是 STATEMENT 吗？不是，默认是 SESSION（Configuration.java:125 与 XMLConfigBuilder.java:278 双重确认）；STATEMENT 模式才在每条最外层查询结束后清理（BaseExecutor.java:169-172）第二讲
5二级缓存原理？namespace 级共享，CachingExecutor 在每个 Cache 外挂 TransactionalCache：事务内 put 只进 entriesToAddOnCommit，commit 才刷入 delegate，rollback 整体丢弃——两阶段提交；默认关闭，需 <cache> 或 @CacheNamespace 显式开启第二讲
6二级缓存默认装饰链长什么样？BlockingCache? → SynchronizedCache → LoggingCache → SerializedCache? → ScheduledCache? → LruCache → PerpetualCache（CacheBuilder.java:118-140）；readWrite=true（XML 不配 readOnly）时值必须可序列化第六讲
7三种 Executor 的区别？SIMPLE 每次新建 Statement；REUSE 按 SQL 文本复用 Statement（statementMap）；BATCH 累积 addBatch，doFlushStatements 统一 executeBatch——且只有 SQL 文本与 MappedStatement 都相同才并入同一条批次（BatchExecutor.java:62）第二讲
8BatchExecutor 的返回值为什么是 Integer.MIN_VALUE+1002？因为 doUpdate 只是 addBatch，尚未真正执行，拿不到影响行数；真实行数在 flushStatements 后从 BatchResult.getUpdateCounts() 取（BatchExecutor.java:43/79）第二讲
9动态 SQL 的原理？XML 被解析成 SqlNode 节点树（if/choose/trim/where/set/foreach/bind），运行期 apply(context) 拼 SQL；isDynamic 为假时启动期固化为 RawSqlSource，为真才用 DynamicSqlSource 每次重算（XMLScriptBuilder.java:65-74）第四讲
10Mapper 接口的原理？JDK 动态代理：getMapper → MapperProxyFactory.newInstance → MapperProxy.invoke → cachedInvoker 缓存 MapperMethod → execute 按 SqlCommandType 转调 SqlSession API；statementId = 接口全限定名 + . + 方法名第五讲
11插件（Interceptor）原理？InterceptorChain.pluginAll 按注册顺序用 JDK 动态代理逐层包裹四大对象（Executor/StatementHandler/ParameterHandler/ResultSetHandler）；Plugin.wrap 用「注解声明的接口 ∩ 目标类继承链接口」决定代理哪些接口，交集为空静默不拦截第六讲
12延迟加载怎么做的？嵌套查询且 lazy=true 时返回 CGLIB/Javassist 代理，ResultLoaderMap 挂起 ResultLoader；getter 触发 load(property) 才真正发起查询；aggressive 或命中 lazyLoadTriggerMethods 则 loadAll第三讲
13嵌套查询和嵌套映射的区别？嵌套查询（select 属性）= 先查主表再按外键逐条查（N+1）；嵌套映射（resultMap 属性）= 一次 join 查出所有行，靠 createRowKey/combineKeys 在内存里组装对象树（DefaultResultSetHandler.java:1138-1169）第三讲
14主键回填的两种方式？useGeneratedKeys=true → Jdbc3KeyGenerator 用 JDBC getGeneratedKeys（仅 INSERT 默认生效）；<selectKey> → 抽出独立语句（id 加 !selectKey 后缀）由 SelectKeyGenerator 在 BEFORE/AFTER 执行第三、四讲
15多参数方法怎么传参？@Param 或天然多参时 ParamNameResolver 构造 ParamMap，同时挂 param1..N 通用名（不覆盖 @Param 名）；单 POJO 原样直传；集合/数组包装成 {collection/list} 或 {array}第五讲

易错点与面试坑

以下都是文档中强调过的反直觉点，每一条对应一个”知道即加分、不知道就翻车”的瞬间； 按优先级排好了，前三条是源码结论与直觉冲突最厉害的地方。 每条都附了”怎么躲”：改法或排障入口，直接可用。

  • 一级缓存默认作用域是 SESSION 不是 STATEMENT（最常被记错的一条）：Configuration.java:125 字段默认值与 XMLConfigBuilder.java:278 的 settings 默认值两处都是 SESSION。这意味着同一 SqlSession 内多次相同查询会命中旧数据（比如中间被别的连接改了库）； 排查”改了库却读到旧值”先问：是不是同一个 SqlSession？把 localCacheScope 设成 STATEMENT 也只是每条最外层查询后清（BaseExecutor.java:169-172），真正的根治是及时 commit/close。
  • 二级缓存事务内不可见：TransactionalCache.putObject 只写本地暂存（TransactionalCache.java:78-81），commit 才刷入（:94-100）； 同一事务里”先写后查同一 namespace”读到的是旧值，这是设计而非 bug；rollback 只丢本事务新增、不动 delegate 旧数据（:102-105）。
  • 二级缓存要求值可序列化：readWrite=true（XML 不配 readOnly 时默认）时 SerializedCache 对出入参做序列化深拷贝（SerializedCache.java:53-65），缓存实体没实现 Serializable 启动不报错、运行期抛 CacheException； 另一个隐蔽代价：读出来的永远是副本，改它不会影响缓存。
  • ${} 就是 SQL 注入面：TextSqlNode.BindingTokenParser 求值后 String.valueOf 直接拼进 SQL（TextSqlNode.java:77-79）； 3.5.19 虽有 injectionFilter 正则校验字段（:30/:83-87），但核心链路两个构造点都传 null（XMLScriptBuilder.java:83、XMLLanguageDriver.java:57），默认不启用，需使用方自行传入 Pattern。
  • BatchExecutor 交替写不同 SQL 不会合成一批：追加条件是”与上一条 SQL 文本和 MappedStatement 都相同”（BatchExecutor.java:62），A/B/A 交替会产生三个批次； 要真批量，先按 SQL 分组循环，且别忘了 doQuery 前会自动 flushStatements（:87）——批量写后紧跟查询会打断批次。
  • 插件注解写错 type 静默不拦截：Plugin.wrap 只代理「注解声明接口 ∩ 目标类实现接口」的交集（Plugin.java:44-52），交集为空原样返回； 插件”没生效”时第一站就查这里，其次查 InterceptorChain 注册顺序（先注册在最外层，InterceptorChain.java:29-34）。
  • Mapper 重复注册直接炸启动：MapperRegistry.addMapper 对同一接口二次注册抛 BindingException（MapperRegistry.java:62-64）——且只对接口生效，非接口静默跳过； XML 与注解混排时靠 "namespace:" + namespace 资源标记避免双加载（XMLMapperBuilder.java:396）。
  • useGeneratedKeys 只对 INSERT 生效：XML 侧默认值是 configuration.isUseGeneratedKeys() && SqlCommandType.INSERT（XMLStatementBuilder.java:93-95），update/delete 写了也白写；多主键列必须同时给 keyProperty（逗号分隔）和 keyColumn。
  • <include> 没有循环检测：XMLIncludeTransformer 递归展开时未做环检测（已通读全类确认），自引用会一路递归到 StackOverflowError（XMLIncludeTransformer.java:62-65）； 大型项目里 <sql> 片段互相 include 时要人工把住关。
  • RowBounds 是大数据量杀手：它先 skipRows 逐行 next() 跳过 offset 再取 limit（DefaultResultSetHandler.java:391-403），offset=100 万就是把 100 万行数据从数据库拉到内存再扔掉； 生产分页要么 SQL 层 limit，要么用插件改写 BoundSql。
  • selectOne 返回多行直接抛异常：DefaultSqlSession.selectOne 查到 >1 行抛 TooManyResultsException（DefaultSqlSession.java:79-82），0 行返回 null； 别在”理论上唯一”的查询上偷懒，唯一性交给数据库索引保证。
  • @Conditional 式排错不适用于 MyBatis，排错看 ErrorContext：ErrorContext 是 ThreadLocal 递归上下文（ErrorContext.java:41-54），异常消息尾部自带 “The error may exist in …” + statement id + SQL； 看不懂报错时先把完整堆栈尾巴读完，再开 logImpl 的 STDOUT_LOGGING 看 SQL 日志。

DefaultSqlSessionFactory —— openSession 的五步装配

DefaultSqlSessionFactory.java:94-109 是 DataSource 路径的唯一实现，五行代码定义了运行期的起点：

// DefaultSqlSessionFactory.java:94-109
  private SqlSession openSessionFromDataSource(ExecutorType execType, TransactionIsolationLevel level,
      boolean autoCommit) {
    Transaction tx = null;
    try {
      final Environment environment = configuration.getEnvironment();
      final TransactionFactory transactionFactory = getTransactionFactoryFromEnvironment(environment);
      tx = transactionFactory.newTransaction(environment.getDataSource(), level, autoCommit);
      final Executor executor = configuration.newExecutor(tx, execType);
      return createSqlSession(configuration, executor, autoCommit);
    } catch (Exception e) {
      closeTransaction(tx); // may have fetched a connection so lets call close()
      throw ExceptionFactory.wrapException("Error opening session.  Cause: " + e, e);
    } finally {
      ErrorContext.instance().reset();
    }
  }
  • 步骤行号：:98 getEnvironment → :99 取 TransactionFactory → :100 newTransaction → :101 configuration.newExecutor（第二讲的装配链在此触发）→ :102 createSqlSession。
  • :104 异常路径必须先 closeTransaction(tx)——newTransaction 可能已经取到连接，直接抛异常不关连接会泄漏（注释原文 “may have fetched a connection so lets call close()”）。
  • DefaultSqlSessionFactory.java:133-138：environment 或 transactionFactory 为 null 时兜底返回 new ManagedTransactionFactory()——没配 <environments> 也能开 Session，这是 Spring 无事务环境下仍能工作的关键。

3.5 不完整元素机制：跨文件引用的救命稻草

MyBatis 允许 statement 引用定义在后面文件的 resultMap/sql，靠的是「不完整元素」队列：

// Configuration.java:999-1016
  public void parsePendingStatements(boolean reportUnresolved) {
    if (incompleteStatements.isEmpty()) {
      return;
    }
    incompleteStatementsLock.lock();
    try {
      incompleteStatements.removeIf(x -> {
        x.parseStatementNode();
        return true;
      });
    } catch (IncompleteElementException e) {
      if (reportUnresolved) {
        throw e;
      }
    } finally {
      incompleteStatementsLock.unlock();
    }
  }
  • statements/cacheRefs/methods 都是单遍 removeIf（:999-1016、:1018-1032、:980-997），解析失败且 reportUnresolved=false 时静默留下；
  • parsePendingResultMaps（:1034-1062）是唯一用 do-while 滚动重试的实现（:1042-1054）：单轮中某个 resolver 失败只暂存异常，只要本轮有成功就再来一轮——因为 resultMap 之间有 extends 继承链，需要”滚动推进”；
  • 每类不完整元素各有一把 ReentrantLock（:169-177），addIncompleteStatement 等四个 add 方法各自加锁（:855-905）。

第二讲：Executor 执行器体系 —— 一级缓存、三种执行器与二级缓存

第二讲小结：缓存分两级、执行器分三种、批量有哨兵

一句话定位：插件靠 InterceptorChain.pluginAll 顺序包裹四大对象（Executor/StatementHandler/ParameterHandler/ResultSetHandler），Plugin.wrap 用「注解接口 ∩ 目标类接口」定位、交集为空静默跳过；二级缓存靠 CacheBuilder 的固定装饰链（Blocking?→Synchronized→Logging→Serialized?→Scheduled?→Lru→Perpetual）给 HashMap 加能力，TransactionalCache 不在构建链上而是 CachingExecutor 会话期挂载，用暂存/延迟清空/补占位实现两阶段提交；日志靠三组 JDK 动态代理在 debug 开启时才织入。

三个最值得记住的点：

  1. 插件”没生效”先查两处：Plugin.wrap（:44-52）注解声明的接口与目标类实现接口交集为空时静默返回原对象——type 写错/写多都不报错；其次查注册顺序（先 add 在最外层，InterceptorChain.java:29-34）。方法级命中靠「声明类 + Method 全等」双条件（Plugin.java:57-58），重载方法必须写全 args。
  2. 装饰链顺序不能凭直觉：实际是 Blocking?→Synchronized→Logging→Serialized?→Scheduled?→Lru→Perpetual（CacheBuilder.java:118-140）——锁和日志在淘汰算法外侧；而 TransactionalCache 不在构建链上，是 CachingExecutor 运行期为每个 Cache 动态挂载的会话级缓冲（CachingExecutor.java:42）。自定义 Cache 实现（type 指定非 PERPETUAL）不加任何装饰器（issue #352，:97），只补 LoggingCache。
  3. TransactionalCache 的两个”延迟”是 BlockingCache 不死锁的关键：clear() 只置 clearOnCommit 延迟到 commit 才清（:88-92）；miss 集合在 commit 时补 null 占位、rollback 时 remove 解锁（:113-133）——前者让 BlockingCache 的等待线程被 put 唤醒，后者让回滚不会把锁永远留在缓存里。
