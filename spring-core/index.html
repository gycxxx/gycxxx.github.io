三条主线（带着这三条线读后面六讲，就不会迷路）：

  1. Bean 创建流：BeanDefinition（配方）→ beanDefinitionMap（配方仓库）→ preInstantiateSingletons（照单全做一遍）→ getSingleton（单例池查/建）→ createBean/doCreateBean（实例化 → 属性填充 → 初始化 → 销毁注册）→ BeanPostProcessor（前后各过一道）→ 入 singletonObjects。第一、二讲。
  2. AOP 代理织入流：@EnableAspectJAutoProxy → AutoProxyRegistrar 注册 APC BeanDefinition → APC 本身是个 BeanPostProcessor → postProcessAfterInitialization 里查出匹配的 Advisor → wrapIfNecessary → DefaultAopProxyFactory 选 JDK/CGLIB → 调用时 DynamicAdvisedInterceptor 跑通知链 ReflectiveMethodInvocation.proceed()。第四讲。
  3. 事务拦截流：@Transactional → AnnotationTransactionAttributeSource 解析成 TransactionAttribute → TransactionInterceptor 作为 MethodInterceptor 进入上一条的拦截链 → getTransaction 按传播行为开/挂起/复用 → DataSourceTransactionManager.doBegin 拿连接关自动提交 → 业务执行 → commit/rollback → doCleanupAfterCompletion 解绑连接。第六讲。

速览：各讲做了什么（先看这个再进细节）

如果只读一张表就要看懂 Spring 核心，就是这张。六讲是一条 Bean 生命周期的六个接力棒——配置文本进来，逐棒加工，最后变成一个带 AOP、带事务能力的单例对象交出去。下面每行一句话讲清这棒在干嘛、接到什么、交出什么。

讲一句话白话收到什么（输入）交出什么（输出）这棒最怕什么
第一讲·BeanFactory 容器造对象的”仓库”：先存一堆配方（BeanDefinition），要货时按名字/类型查配方、按需造对象、放进单例池；循环依赖靠三级缓存兜底XML 里的 <bean> / 注解扫描出来的类名 + BeanDefinition单例池 singletonObjects 里可复用的对象；以及一份”按类型查名字”的索引覆盖注册同名 Bean、循环依赖没开 allowCircularReferences、原型 Bean 循环引用（直接抛异常）
第二讲·生命周期与注入对象的生产线：实例化（选构造器）→ 属性填充（@Autowired 在这里）→ 初始化（Aware 回调 / @PostConstruct / init-method）→ 登记销毁（@PreDestroy）BeanDefinition + BeanFactory + 已注册的 BeanPostProcessor一个初始化完毕的 bean（或它的代理），以及一条销毁回调链循环依赖遇到 AOP（要代理但代理还没造好）、构造器注入失败、@Value 占位符解析不出来
第三讲·ApplicationContext 与资源仓库的”店长”：跑一遍 refresh() 十二步开场（登记后处理器、初始化事件总线、预实例化全部单例），并负责把 @Component/@Configuration 扫进来、把资源路径解析成文件一堆 XML / 配置文件路径 + 一批带注解的类一个完全启动好的上下文，getBean 直接能拿到后处理器注册顺序错、扫描漏包、@Bean 方法被当成普通工厂方法（lite 模式）
第四讲·AOP 代理体系给 bean “套壳”：不是改字节码，而是在 bean 外面生成一个代理对象；调用先打到代理，代理按切点匹配决定”执行业务”还是”跑通知链”一个初始化好的 bean + 一堆切面（Advisor）一个代理对象（实现接口的 JDK 代理 / 是子类的 CGLIB 代理）类或方法 final（CGLIB 套不上）、代理没暴露、exposeProxy 没开导致 AopContext 取不到
第五讲·SpEL 与切面解析切点表达式 execution(* com.x..*.*(..)) 的”语言引擎”：解析成 AST、类型匹配时求值；同时 @Aspect 类上的 @Pointcut/@Before 被翻译成 Advisor一个字符串表达式 + EvaluationContext（根对象、变量、Bean 引用）Expression 对象 / boolean 匹配结果 / 属性方法值表达式的 .. 通配写错、根对象为 null、@Value("${}") 占位符和 SpEL 混用时顺序错
第六讲·声明式事务给方法套一层”要么全成要么全败”：代理拦截后按传播行为开事务（拿 JDBC 连接关自动提交），方法正常就 commit、抛异常就 rollback@Transactional 注解 + 一个 PlatformTransactionManager已提交/已回滚的事务；TransactionSynchronizationManager 里挂好的线程级连接自调用不走代理、抛受检异常不回滚、传播行为配错、rollback-only 被内层污染

第四讲是个枢纽：没有 AOP 代理，第五讲和第六讲就都无从谈起——切面和事务都只能通过”方法调用被拦截”生效。第六讲的 TransactionInterceptor 本质上就是一个普通 MethodInterceptor，它挂在第四讲生成的拦截链上；第五讲的切点表达式则是”这条链拦哪些方法”的裁判。所以顺序上是”一→三→二→四→五/六”，逻辑上是”一→二→四→六→五（用时）”。

面试速通：Spring 核心高频问题一页纸

一句话定位：Spring 核心六讲是一条 Bean 生命周期的接力——配置文本进来，逐棒加工，最后变成一个带 AOP、带事务能力的单例对象交出去。 面试被问”Spring 核心学了什么”，先给这条主线；被追问任何细节，再按讲次展开：

  1. Bean 创建流：BeanDefinition（配方）→ beanDefinitionMap（配方仓库）→ preInstantiateSingletons（启动时照单全做）→ getBean → 实例化 + 注入 + 初始化 → 入单例池（第一、二讲）；
  2. AOP 代理织入流：自动代理创建器本身是个 BeanPostProcessor，在 bean 初始化后把它换成代理，调用时按切点匹配跑通知链 ReflectiveMethodInvocation.proceed（第四、五讲）；
  3. 事务拦截流：TransactionInterceptor 挂在同一条拦截链上，按传播行为拿连接、关自动提交、提交或回滚（第六讲）。

三条线合起来就是”一次 getBean + 一次方法调用”的全过程。阅读顺序是一→三→二→四→五/六，逻辑枢纽是第四讲：没有代理，切面与事务都无从谈起——它们都只能通过”方法调用被拦截”生效。

易错点与面试坑

以下都是文档里强调过的反直觉点，按出题频率从高到低排列。 每条都值得在面试里主动说——它们是”背过源码”与”只会背八股”的分水岭。

  • @Transactional 自调用不生效：this.method() 是裸对象调用、不过代理，TransactionInterceptor 只拦代理的入口； exposeProxy 也只是让 AopContext.currentProxy() 可用，仍要手动取目标再手动调，很少有人这么写； 这与 AOP 切面的自调用失效是完全相同的机制——TransactionInterceptor 本身就是一个普通 MethodInterceptor； 标准解法：注入自身代理，或改用 TransactionTemplate（编程式事务的显式回调没有自调用问题）。
  • Spring 6.0 起 @Transactional 只认 public 方法：publicMethodsOnly 默认 true，非 public 方法上的注解被静默忽略； 这是 5 → 6 升级后”事务突然不生效”的最常见原因，Spring 5 时代”用 CGLIB 代理非 public 方法”的技巧就此失效； 想要非 public 方法的事务，只能显式关掉 publicMethodsOnly； 官方推荐的正解是保持方法 public，配 proxyTargetClass=true（Spring Boot 默认）。
  • 默认只在运行时异常回滚：rollbackOn 只对 RuntimeException/Error 返回 true，受检异常不回滚，要显式 rollbackFor； 业务异常若是受检异常又忘了配 rollbackFor，就是”抛了异常、数据却已提交”的经典事故； 反过来 Error 会回滚也常被忽略——它属 unchecked； 回答时把”默认规则 + 两个例外（受检不回滚、Error 回滚）“一起说，才算完整。
  • 方法内 try-catch 吞异常，可能吞出 UnexpectedRollbackException：内层 setRollbackOnly 后即使正常返回， 外层 processCommit 发现 globalRollbackOnly 也会抛异常——这就是”没抛业务异常却回滚了”的确切机制； 异常被 catch 不等于事务被挽救，rollback-only 标记会顺着调用链冒泡到最外层； catch 后要么重抛匹配回滚规则的异常，要么显式标记回滚，别装作什么都没发生。
  • CGLIB 不能代理 final 类/final 方法：public final 方法会打 WARN 且调用不路由到目标（可能 NPE）， 父类继承链上任意一层的 final 都会被递归检查到；private 方法同理拦不到； JDK 代理的边界则是”只代理接口方法”——没接口时 Spring 会从公有方法签名反推接口，也可能推导失败； 选型前先看目标类有没有接口、是不是 final，这是 AOP 排错的第一步。
  • 循环依赖 + AOP 有经典矛盾：早期给出去的是原对象、最终容器里放的是代理； Spring 6+ 默认容忍这种不一致（allowRawInjectionDespiteWrapping），代价是注入字段可能停在”原对象上的 null”； 这也是 @Autowired 字段运行期发现全是 null 的经典根因之一； 严格模式下这段会直接抛 BeanCurrentlyInCreationException，报错信息就是那段”raw version … wrapped”的话。
  • 构造器注入遇到循环依赖必炸：构造器注入发生在实例化阶段，早于二级缓存挂载，三级缓存来不及救； 只有字段注入才可能被三级缓存救——“构造器注入更好”与”它可能撞循环依赖”两件事同时成立； 这也是”Spring 推荐构造器注入、线上却有团队选字段注入”的现实理由； 面试时把”实例化早于缓存挂载”这个时序讲清楚，比背结论更有说服力。
  • doCleanupAfterCompletion 必须还原 autoCommit 与隔离级别：否则连接还池后污染下一个用户，出各种诡异问题； 内层参与方有 isNewConnectionHolder 双重守卫，绝不解绑也不关掉外层的连接——参与方永远动不了别人的事务现场； cleanupAfterCompletion 本身还有第二道守卫：clearSynchronization 只在 isNewSynchronization 为真时执行； “连接池中毒”的防线就是这两行还原，答题时值得主动提。
  • lite 配置类里 @Bean 互相调用会造出两个对象：没有 CGLIB 那层”查容器”，每次调用都新建； “@Bean 方法总是返回单例”只对 full 配置类成立，proxyBeanMethods=false 时这个承诺作废； full/lite 的唯一判据就是 proxyBeanMethods 是否为 false，@Component/@ComponentScan 等只是 lite 的触发条件之一； 看到”注入了两个不同实例”的 bug，先查配置类是不是被写成了 lite。
  • 事务上下文不跨线程，AFTER_COMMIT 也回滚不了：TransactionSynchronizationManager 是 ThreadLocal， 线程池/@Async 里事务不生效，rollback-only 也不会跨线程传递； triggerAfterCommit 在 doCommit 之后，此刻发 MQ 失败已无法回滚——分布式一致性在 Spring 里的具体落点； 这类场景要么接受最终一致，要么把发消息挪进事务内、用业务表做补偿。

第一讲：BeanFactory 与容器基础 —— BeanFactory / DefaultListableBeanFactory / BeanDefinition

先说人话：本讲每个阶段在干什么

把 IoC 容器想象成一家中央厨房：BeanDefinition 是菜谱（写明”要做什么菜、用什么料、几分熟”），beanDefinitionMap 是菜谱柜（按菜名编号存放），singletonObjects 是不锈钢保温台（做好的菜放这儿，谁来拿都是同一份），getBean 是窗口叫号（报菜名或报想吃什么口味，后厨照单做菜）。厨房的规矩是：先看保温台有没有（命中就直接给），没有就看柜子里有没有菜谱，有菜谱就照做，做好了放保温台。

本讲主线：菜谱（BeanDefinition）进柜子（beanDefinitionMap），叫号（getBean）时照菜谱做菜（createBean），做好放进保温台（singletonObjects），下次直接拿。

三个最值得记住的点：

  2. 对每个切面，遍历它的所有方法，按注解分类：

关键结论：Spring AOP 里”切面自己调用自己的方法”不会走代理，因此：

@Aspect @Component
public class LogAspect {
    @Around("execution(* com.x.Service.*(..))") Object around(ProceedingJoinPoint pjp) throws Throwable {
        return pjp.proceed();
    }
    @Before("execution(* com.x.Service.*(..))") void before() { /* 不会被 around 触发 */ }
}

around 走代理触发，before 不会——因为 pjp.proceed() 之后的调用链还是代理链；而如果 around 里直接 this.before()，那更是裸调用。这与 @Transactional 自调用失效是完全相同的机制（TransactionInterceptor 就是一个 MethodInterceptor）。

  3. 只有 @Around 能改控制流。@Before/@AfterReturning/@AfterThrowing/@After 分别生成 MethodBeforeAdvice/AfterReturningAdvice/ThrowingAdvice/AfterAdvice（由 BeanFactoryAspectJAdvisorsBuilder 生成），它们都在 ReflectiveMethodInvocation.proceed 的前后”伴随”，不能阻止 proceed()；只有 @Around 生成 MethodInterceptor 并自己决定调不调 proceed()。Spring AOP 的”自调用不生效”就源于此——this.before() 是裸对象调用，不过代理。

第六讲：声明式事务 —— PlatformTransactionManager / @Transactional

先说人话：本讲每个阶段在干什么
