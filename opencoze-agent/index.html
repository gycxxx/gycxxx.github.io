〇、全景地图

先说人话：这个模块是干什么的

你在 Coze 类平台上拖拖拽拽配出来的一个”智能体”——选模型、写人设 Prompt、挂插件、挂知识库、设变量、开建议问题——在 OpenCoze 里就是一个 SingleAgent 配置对象。

这个模块负责把这份配置变成一次真正能跑的对话：

  1. 构建期：读配置 → 装配工具 → 声明节点 → 连边 → 编译成一张可执行的图（Eino compose.Runnable）；
  2. 运行期：一次用户提问 → 图执行 → 各种事件（函数调用、知识、回答分片、建议问题、中断）通过回调写进一个 Pipe → 上层会话侧消费并转成 SSE 吐给前端。

最关键的一句话：agent_flow_runner.go:129 把图自己的返回值整个丢弃了（_, _ = r.runner.Stream(...)）——所有对外的可见输出只通过 callback 写出。理解这一点，是读懂本模块的钥匙。

高频 Q&A（先结论）

#问题结论
1图编排是自研的吗？不是。基于 CloudWeGo Eino compose（go.mod:20，v0.4.8）。ReAct 用的是官方 flow/agent/react。
2Agent 有几种数据形态？三种：Draft（single_agent_draft 表，一 agent 一行）、Version（single_agent_version 表，发布时整行深拷贝的不可变快照）、Publish（single_agent_publish 表，发布动作账本，含 channels）。
3领域实体里有什么字段？几乎没有。entity.SingleAgent 只组合了 *model.SingleAgent（entity/single_agent.go:24-26），真身在 crossdomain/agent/model/single_agent.go:56-82。
4有工具和没工具的图有什么区别？有工具 → 用 Eino 官方 react.NewAgent 导出一个子图挂进主图（agent_flow_builder.go:177-189）；无工具 → 只挂一个裸 ChatModel（:234）。
5为什么四个前置节点是并行的？编译选项里写了 WithNodeTriggerMode(compose.AllPredecessor)（agent_flow_builder.go:272），prompt_template 必须等全部前驱完成才触发。
6对外输出从哪来？只从 callback 来。agent_flow_runner.go:129 把 runner.Stream 的返回值整个丢弃了。
7流式管道多大？会话侧 Pipe(20)（agent_run_impl.go:49-74），agentflow 侧 Pipe(10)（callback_reply_chunk.go:44）。
8有几种事件类型？8 种（crossdomain/agent/model/single_agent.go:31-40）：chatmodel_answer / tools_as_chatmodel_answer / tool_mid_answer / tools_message / func_call / suggest / knowledge / interrupt。
9知识检索是工具吗？不是。是构建期无条件挂上的图节点 knowledge_retriever。node_tool_knowledge.go 里的 newKnowledgeTool 全仓无调用点（死代码）。
10建议问题在哪解析？在 callback 里（callback_reply_chunk.go:376-402 做 JSON 反序列化），图上的 suggest_parser 只是透传（node_suggest_parser.go:25-28）。
11数据库工具怎么防越权查表？运行时用 sqlparser 解析 SQL 的表名，与工具绑定的表名不相等就报错（node_tool_database.go:86-88）。
12草稿和线上的工具执行怎么隔离？靠 ExecScene 字段：草稿走 ExecSceneOfDraftAgent，线上走 ExecSceneOfOnlineAgent（node_tool_plugin.go:127-132）。
13每次请求都会重建图吗？是的。single_agent_impl.go:96-136 每次请求都 BuildAgent，图没有任何缓存。
14中断（Interrupt）怎么传递？走 error 通道：compose.ExtractInterruptInfo(err) 从子图 extra 里取（callback_reply_chunk.go:73），再转成 EventTypeOfInterrupt。
15多模态输入不支持会怎样？降级成文本拼进 Content（agent_flow_runner.go:255-273）。注意 isSupportFile() 硬编码 return false（:293），文件输入永远降级。

易错点与面试坑

  1. 以为 newKnowledgeTool 提供了 recallKnowledge 工具：它全仓无调用点（node_tool_knowledge.go:47），是死代码。真实的知识检索是构建期强制节点。
  2. 改了 callback 忘了 output.Close()：非目标节点必须显式 Close（callback_reply_chunk.go:186-189），否则下游 Pipe 阻塞泄漏——这是改 callback 时的硬性不变量。
  3. 以为 req.Variables 会生效：single_agent_impl.go:126-134 从未给 exeReq.Variables 赋值，所以 node_persona_render.go:41 的一级查找永远失效，只能走 :46 兜底。
  4. 以为 {{ name }} 能取到变量：extractJinja2Placeholder 做了 trim 校验却 append 了未 trim 的 match[1]（agent_flow_builder.go:294），{{ name }} 会提取出 " name "，查表取不到值。
  5. 并发发布：publish.go:100 的 err 是共享外层变量（循环变量未遮蔽），Mutex 只保护了 map——典型并发写共享变量隐患。
  6. 发布失败对前端不可见：publish.go:122 的 _ = tasks.Wait() 丢弃了所有错误，且 :139 恒返回 CheckNotPass: false。
  7. knowledgeConfig == nil 会 panic：node_retriever.go:57 在 :60 的 nil 判断之前就解引用了 r.knowledgeConfig。
  8. Draft ↔ Version 的 PO 转换不对称：singleAgentVersionPo2Do 未映射 BackgroundImageInfoList（dal/single_agent_version.go:85-113），而 draft 侧映射了（:158）——线上版本读回会丢背景图。
  9. 以为 Reserve/Interrupt 会处理多个工具中断：callback_reply_chunk.go:244 无脑 break，多工具同时中断只保留第一个。
  10. ValidateAgentDraftAccess 的返回值：非创建者会返回 do 与 err 同时非 nil（application/singleagent/single_agent.go:550-557），调用方只看 do 会误放行。

第一讲：数据模型 —— Draft / Version / Publish 三形态

先说人话：本讲每个阶段在干什么

读代码最容易被绕晕的是：同样一个”Agent”，代码里有 SingleAgent、SingleAgentDraft、SingleAgentVersion、SingleAgentPublish 四个名字相近的东西，而且 entity 包里的实体几乎是空的。

本讲先解决这个命名混乱：

  1. entity.SingleAgent —— 只是个壳，字段在跨域层；
  2. Draft / Version / Publish —— 分别是”可编辑态 / 不可变快照 / 发布账本”，对应三张表；
  3. 事件枚举与 Interrupt 类型 —— 这是 agentflow 与上层通信的唯一协议。

把这三点理清，后面所有流程里的”传进来一个 agent”才知道传的到底是什么。

第四讲：五类工具节点 —— 工具是怎么”长”进图里的
