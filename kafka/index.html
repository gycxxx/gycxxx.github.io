三条主线：

  1. 数据流：record 序列化 → 进 RecordAccumulator 批次 → ProduceRequest 过网络 → KafkaApis.handleProduceRequest → ReplicaManager.appendRecords → UnifiedLog.append → LogSegment 落盘 → 等 ISR ack → ProduceResponse 回客户端
  2. 控制流：字节流 → Processor 解析 RequestHeader → requestQueue → KafkaRequestHandler → KafkaApis 按 ApiKeys 分发 → 同步/异步（Purgatory/CompletableFuture）→ Response 回 responseQueue → Processor 写 socket
  3. 恢复流：broker 崩溃 → 重启后 LogManager.loadLogs 按 recovery-point 截断恢复分区 → 未提交事务标记清理；controller 崩溃 → raft 重新选主 → 新 leader 重放 __cluster_metadata 日志/snapshot 重建内存镜像 → broker 通过 BrokerRegistration/BrokerHeartbeat 重新注册

面试速通：Kafka 高频问题一页纸

这是一张”先给结论、被追问再按讲次展开”的速查卡：以下所有一句话结论均提炼自各讲小结的”三个最值得记住的点”与端到端演算， 追求 30 秒能答、答完能指路；本页是索引不是正文——任何结论被追问细节，必须回到对应讲次精读， 尤其是该讲的”端到端演算”，它把结论串成了可复述的故事。

高频 Q&A（先结论）

#面试问题一句话结论深入
1ISR 与 HW/LEO 是什么关系？ISR 是与 leader 保持同步的副本集合，follower 追平后 leader 才推进 HW；消费上界按隔离级别分别取 LEO/HW/LSO第一讲、第三讲
2acks=all 的语义？等 ISR 中足够多副本追平 requiredOffset 才返回（框架统一走 DelayedProduce 逐分区检查）；acks=0 时 broker 回 NoOpResponse，出错只能靠断连让 producer 感知第一讲
3幂等 Producer 怎么去重？pid+epoch+sequence 三元组；sequence 只在首次 drain 时分配、重试带原序号重发，broker 侧 ProducerStateManager 发现序号已见即判重短路，返回已落盘 offset第四讲、第三讲
4事务 Producer 的两阶段？EndTxn → PREPARE_* 先落 __transaction_state 日志 → 向所有参与分区广播 TransactionMarker → COMPLETE_*；PREPARE 状态是崩溃恢复的锚点，重启后必须补发未写完的 marker第六讲
5Consumer Group rebalance 流程？classic 协议：JoinGroup 上报订阅、SyncGroup 由 leader 算好分配分发全员、Heartbeat 保活；new 协议（KIP-848）：单个 ConsumerGroupHeartbeat 由 broker 指派目标、客户端增量执行并心跳 ack第五讲
6Kafka 为什么快？五层叠加，缺一层都会掉一个量级：①顺序追加，数据只往 .log 尾部写，顺序写是磁盘最快模式；②攒批，producer 侧 RecordAccumulator（RecordAccumulator.java:68）分区别队+内存池+sticky 分区（:275/:302/:333），Sender 按节点 drain（:852-937）把随机写并成批量顺序请求；③分区即并行单元，多分区可并行 append，partition 数就是写入并行度；④读侧零拷贝，LogSegment.read（LogSegment.java:431）slice 出共享同一 FileChannel 的视图（不拷字节），FileRecords.writeTo（FileRecords.java:302）走 transferFrom，明文路径直落 fileChannel.transferTo(position, count, socketChannel)（PlaintextTransportLayer.java:213）——sendfile 全程不过用户态；TLS 加密时这条快路径失效，退化成先解密再写（SslTransportLayer.java:1003，TransferableChannel.java:39 注释明说 fast path 只对 JDK 内部类生效）；⑤读路径轻，.index 每 4KB 一条稀疏记录，查找先二分再小范围顺序扫；压缩批 broker 侧只做 CRC/压缩类型初检（UnifiedLog.java:1128），不逐条解压。另外全程读写优先命中 OS page cache，刷盘交给内核第三讲、第四讲
7KRaft 模式解决了什么？4.3.1 已纯 KRaft（无 ZooKeeper）：控制面完全由 __cluster_metadata-0 这一条 raft 日志驱动，controller 是唯一写者、单线程事件队列保证”先应用后响应”的顺序一致第二讲
8分区副本同步与 leader 选举？offset 只在 leader 分配且必须持锁，follower 只校验 offset 衔接（不衔接抛 UnexpectedAppendOffsetException）；leader 变更后按 leader epoch cache 截断恢复，新 leader 由 controller replay 记录时选出第二讲、第三讲
9log 在磁盘上的结构？一个分区一个目录，每个 segment 四件套 .log/.index/.timeindex/.txnindex，外加 producer 状态 .snapshot；索引是稀疏的，不是每条消息都有第三讲
10日志压缩（compact）怎么做？按 key 保留最新值：buildOffsetMap 用 SkimpyOffsetMap 记每个 key 最后一次 offset → 按大小分组 → cleanSegments 写 .cleaned 新段再原子替换，checkpoint 保证不重复压缩第三讲
11rebalance 有什么坑？eager 协议停整个世界：全组两轮 join、一次性撤销全部分区再重新分配；cooperative-sticky 只撤销待移动分区，2-3 轮心跳收敛，其余分区全程不停顿第五讲
12为什么消费会重复？position 随 fetch 读取前进，而不是随 commit 前进；commit 只是把当前位置”存档”供重启/再均衡后恢复，两者之间的窗口就是重复消费窗口第五讲
13READ_COMMITTED 为什么消费不到最新数据？读上界是 LSO 而非 LEO，未完结事务（Begin 后无 End）会卡住 lastStableOffset 不前进；aborted 事务靠 .txnindex 在读取时过滤——存储引擎不删数据，只是”不让你看”第三讲、第六讲
14如何防僵尸 producer？pid fence 靠 epoch 单调递增：InitProducerId 对同一 transactionalId 总是提升 epoch，旧 producer（哪怕是僵尸）的任何请求都被拒收 PRODUCER_FENCED第六讲
15Kafka 如何实现顺序消费？保序的两级保证：producer 侧同一分区单 in-flight（max.in.flight.requests.per.connection ≤ 5 + 幂等靠 sequence 重排序，乱序也能纠正）；consumer 侧单线程单分区——分区是顺序的最小单元，一个分区同时只被一个消费者消费，多线程消费同一分区就破序。要全局顺序只能单分区，要吞吐就按 key 哈希分区保”相关消息”有序第四讲、第五讲
16Kafka 如何保证消息不丢失？三段各设防线：producer acks=all + retries 拉满 + 发送失败回调兜底；broker min.insync.replicas ≥ 2（ISR 至少两个副本 ack 才认）、unclean.leader.election.enable=false（不许落后副本当选）；consumer 关自动提交、业务处理成功后手动提交 offset（先处理后提交，重复好过丢失）。全链闭合才叫不丢第一讲、第五讲
17Kafka 消息的发送过程简单介绍一下？producer send() 只是把 record 塞进 RecordAccumulator：序列化 → 按分区器选分区 → 挂到分区别队或新建批次（RecordAccumulator.java:275）→ 后台 Sender 线程按 broker 节点 drain 批次（:852-937）凑成 ProduceRequest → 过网络到 broker → KafkaApis.handleProduceRequest → ReplicaManager.appendRecords → UnifiedLog.append 落盘 → 等 ISR ack 到 requiredOffset → ProduceResponse 回客户端（acks=all 时 DelayedProduce 会挂起等满足条件）第四讲

使用方式：先答”一句话结论”，面试官点头即过；一旦追问，按右列”深入”跳到对应讲次， 优先看该讲的端到端演算——它是把结论串成故事的最佳素材。四个最高频的追问方向：

  • ISR/HW/acks 被追问 → 第一讲”一条 acks=1 的 produce 请求”十步演算，看 DelayedProduce 如何等 requiredOffset、 HW 如何被 follower 追赶推进，以及响应如何经三级队列回到 socket；
  • 幂等/重试被追问 → 第四讲”幂等 producer 重试一次网络超时”五步演算，看 sequence 为什么不重新分配、 broker 侧如何对已见序号判重短路并返回已落盘 offset；
  • rebalance 被追问 → 第五讲”3 消费者组的一次 cooperative-sticky 扩容”六步演算，看为什么只有分区 2、3 经历撤销-移交、 其余四个分区的消费从未停顿；
  • 事务被追问 → 第六讲”consume-transform-produce 事务”八步演算，看 PREPARE 状态如何在崩溃重启后兜底补发 marker、 位移如何以挂起态落定。

易错点与面试坑

  • HW 不前进 ≠ 没数据：acks=all 下 follower 掉队会卡住 DelayedProduce 的 requiredOffset，produce 侧表现为超时重试而非立即报错； 排查先看 ISR 进度与副本追赶，而不是反复重发或怀疑丢数据。
  • READ_COMMITTED 的上界是 LSO 不是 LEO：未完结事务（Begin 后无 End）会卡住 lastStableOffset，消费者看到”生产成功但消费不到”； 此时查 fetch 配置毫无意义，要等事务落定，或去 .txnindex 看有没有 aborted 批次。
  • timeindex 同样是稀疏的：与 offset 索引一样每 4KB 才记一条 timestamp→offset，按时间戳查 offset 只能二分定位后小范围扫描； 指望按时间戳精确命中某条消息是不现实的。
  • 重试批次不重新分配 sequence：幂等的全部秘密就在”序号只在首次 drain 分配”这六个字； 没有幂等时，同样的重试就是真实的重复消息——这正是 KIP-98 引入 pid+sequence 的动机。
  • offset 只在 leader 分配且必须持锁：follower 只校验衔接，不衔接直接抛 UnexpectedAppendOffsetException； 同一 offset 在全集群只有一个”正统”写入者，这也是 leader 变更后必须截断恢复的原因。
  • 事务 ≠ 端到端恰好一次：事务保证的是”位移提交与数据写入原子”，消费侧崩溃重拉仍可能重复处理； 面试时把 Kafka 事务说成”实现 exactly-once”是常见扣分点。
  • 删除绝不碰高水位之上：deleteOldSegments 的谓词再激进也不会删 HW 之上的段，log start offset 只随删段单调前进； “数据还在磁盘上”和”你能读到”是两回事，别把 retention 到期和可读性混为一谈。
  • 手动 assign 没有组概念：hasAutoAssignedPartitions 是两套协议的分水岭，手动 assign 完全不进协调器世界； “用了 KafkaConsumer 就会 rebalance”是想当然，被问到时先确认对方的订阅方式。

5. Purgatory —— 请求完成等待机制

两个最常用的具体化：

  • DelayedFetch（core/src/main/scala/kafka/server/DelayedFetch.scala:41）：tryComplete()（:68-144）枚举了 Case A–H——不再是 leader、副本没了、epoch 被 fence、fetch offset 落在旧段、累计字节达到 minBytes（Case G，:139-141）等。maxWaitMs 到期则由 ExpiredOperationReaper 强制完成，返回已有数据。

QuorumController（metadata/src/main/java/org/apache/kafka/controller/QuorumController.java:175）是控制器的大脑，核心机制有三：

(a) 单线程事件队列。所有写操作经 appendWriteEvent（:960）进入队列，实际执行在 ControllerWriteEvent 上；raft 提交回调 QuorumMetaLogListener.handleCommit（:975）同样入队——先应用后响应，保证顺序一致。

(b) 记录应用 replay。replay(ApiMessage, Optional<OffsetAndEpoch>, long)（:1213-1309）是一个按 MetadataRecordType 分发的 switch，把每种记录喂给对应 ControlManager：RegisterBrokerRecord → clusterControl、TopicRecord/PartitionChangeRecord → replicationControl、ConfigRecord → configurationControl、BeginTransactionRecord → offsetControl 等。启动/追赶时先 handleLoadSnapshot（:1032）重放快照，再重放其后的日志。

(c) 元数据日志事务 + 快照。appendRecords（:897）区分原子/非原子写入；OffsetControlManager（metadata/src/main/java/org/apache/kafka/controller/OffsetControlManager.java:47）管理”最后提交偏移/最后稳定偏移”：controller 当选时 activate 会在最后稳定偏移处创建内存快照（:252），每次 handleScheduleAppend 后也 idempotentCreateSnapshot（:305），maybeAdvanceLastStableOffset 时清理更旧的快照（:328）。这些内存快照正是落盘 snapshot 文件（__cluster_metadata-0/<offset>-<epoch>-checksum.checkpoint）的数据源，供 follower 与重启后快速加载。未提交事务（Begin 后无 End）会卡住 lastStableOffset 不前进，对应 TransactionState 的 PREPARE 语义（第六讲）。

第三讲小结：稀疏索引 + 幂等去重 + 分段压缩三位一体

一句话定位：UnifiedLog 把”顺序追加 + 按 offset 读”压缩到极致——数据只进 .log，索引按字节间隔稀疏记录，事务与 producer 状态各自有专门索引；删除是段级的（log start offset 单调前进），压缩是分组重写 + offset map 判活，两者都绝不触碰高水位之上的数据。

2. RecordAccumulator —— 批次、内存池与 sticky 分区

  • 无指定分区时问 BuiltInPartitioner.peekCurrentPartitionInfo（:302）要一个”粘性”分区——同一个批次容量内尽量都写同一个分区，减少小请求；
  • 先 tryAppend 往队尾未满批次追加（:319）；失败则 free.allocate(size, maxTimeToBlock)（:333）从内存池申请 buffer（池满则阻塞到 max.block.ms，这是 producer 端背压），appendNewBatch（:345、:375）新建 ProducerBatch 入队；
  • RecordAppendResult 带回 batchIsFull/newBatchCreated，供上面决定是否 wakeup Sender。

drain（:959）由 Sender 调用，drainBatchesForOneNode（:852）逐节点收集可发送批次：

  • 每个分区同一时刻只有一个 in-flight 批次（:868 isMuted(tp) 跳过），这是保序的关键；
  • 单节点累计不超过 maxRequestSize（:889）；
  • 幂等/事务 producer 在此分配 pid+epoch+sequence：batch.setProducerState(...)（:918）与 transactionManager.incrementSequenceNumber（:919）；

端到端演算：幂等 producer 重试一次网络超时

设 enable.idempotence=true、acks=all、max.in.flight=5，pid=42、epoch=0，分区 orders-1 当前 nextSequence=101。

  1. send() 把 record 追加进 orders-1 的 ProducerBatch（序号 101），返回 future；
  2. Sender drain 该批次，setProducerState((42,0), 101)，nextSequence→102，组成 ProduceRequest 发往 leader，登记进 inFlightBatches["orders-1"]；
  3. 请求发出但响应丢失，delivery.timeout.ms 未到 → Sender 重试：批次重新入队，再次 drain 时 hasSequence 为 true，不重新分配 sequence（RecordAccumulator.java:903 的判断），仍带 (42,0,101) 发出；
  4. broker 侧 UnifiedLog.analyzeAndValidateProducerState 发现 pid=42 的已见序号恰为 100，来件 101 正常衔接 → 正常落盘；假设 broker 其实收到过第一次请求，则第二次到达时发现 sequence 101 已存在 → 判为重复，返回已落盘的 offset 而不重复写入（UnifiedLog.java:1247-1254）；
  5. 客户端收到响应（无论哪一次），completeBatch 用 offset 填 RecordMetadata，future 完成，回调执行。用户侧永远看到恰好一次逻辑写入，即使物理上可能有重复请求。

1. poll 主循环 —— ClassicKafkaConsumer

KafkaConsumer.poll（KafkaConsumer.java:904）只是转 delegate.poll(timeout)。classic delegate 的实现 ClassicKafkaConsumer.poll（internals/ClassicKafkaConsumer.java:640）是一个 do-while 循环（:656-681）：

do {
  updateAssignmentMetadataIfNeeded(timer, false)   // :660 保证 assignment 与 fetch 位置就绪
  fetch = pollForFetches(timer)                     // :662 拉数据
  if (!fetch.isEmpty()) {

三个关键点：

  • updateAssignmentMetadataIfNeeded（:695）= coordinator.poll(timer, ...)（处理加入组/再均衡/自动提交）+ updateFetchPositions(timer)（给没有位置的分区初始化 offset：已提交位移 → 否则按 auto.offset.reset）；
  • pollForFetches（:706）：先 collectFetch() 看缓冲有没有现成数据，没有就 sendFetches() 发请求，然后 client.poll(pollTimer, ...) 阻塞等待——poll 的超时实际花在网络等待上；
  • 提前发送下一轮（:670-672）：用户处理数据时后台已在拉下一批，这是消费吞吐的关键技巧。

2. Fetcher —— 位置管理与分页拉取

Fetcher（internals/Fetcher.java:59，继承 AbstractFetch）只做两件事：

  • sendFetches()（:105）：prepareFetchRequests() 按节点聚合分区（受 max.poll.records、fetch.max.bytes、fetch.min.bytes 约束），带上增量 fetch session（KIP-227，会话内只传变化的 partition，大幅降低大集群开销），发出请求；
  • collectFetch()（:145）：把 FetchBuffer 里已 complete 的 fetch 交给 FetchCollector 反序列化、更新 position（消费位置随读取前进，而非随 commit）、按 max.poll.records 截断。

位置（position）不变量由 SubscriptionState（internals/SubscriptionState.java:74）维护：每个分区有 TopicPartitionState（:1013 起），内含 FetchPosition 与 FetchState（INITIALIZING/FETCHING/AWAIT_RESET/AWAIT_VALIDATION 等，:1033）。订阅模式由 assignFromSubscribed（:315，再均衡后服务端分配）与 assignFromUser（手动 assign）两条路写入；hasAutoAssignedPartitions（:512）区分两种模式——这决定了后面走不走再均衡。

3. ConsumerCoordinator —— classic 协议

ConsumerCoordinator（internals/ConsumerCoordinator.java:103）的 poll（:511-577）是每次用户 poll 的固定动作：maybeUpdateSubscriptionMetadata（刷新订阅）→ 若为自动分配则 ensureActiveGroup（:552，内部完成 FindCoordinator → JoinGroup → SyncGroup）→ maybeAutoCommitOffsetsAsync（:575，enable.auto.commit 的定时提交）。

classic 协议的四个请求都在 broker 的 GroupCoordinator 上完成（第六讲）：JoinGroup 上报订阅与元数据、SyncGroup 由 leader 把 assignor.assign(...) 的结果分发给全员、Heartbeat 保活、OffsetCommit/OffsetFetch 落位移。心跳线程（BaseHeartbeatThread 子类）与用户线程并行：用户线程负责重均衡与拉取，心跳线程只发 Heartbeat 并检测 REBALANCE_IN_PROGRESS——检测到就唤醒用户线程重新 join。

4. new 协议（KIP-848）—— ConsumerMembershipManager

新协议不再有 JoinGroup/SyncGroup 两阶段，而是单个 ConsumerGroupHeartbeatRequest 包打天下：

  • ConsumerHeartbeatRequestManager（internals/ConsumerHeartbeatRequestManager.java:50）按 heartbeat.interval.ms（默认 5s）发送心跳，请求里带订阅 topic、已分配分区、ack 状态；
  • ConsumerMembershipManager（internals/ConsumerMembershipManager.java:108）维护成员状态机 MemberState（internals/MemberState.java:27）：UNSUBSCRIBED → JOINING → RECONCILING → ACKNOWLEDGING → STABLE（:35-71，合法迁移表在 :120-122）；
  • onHeartbeatSuccess（:216）处理 broker 返回的 target assignment：有新目标 → RECONCILING，本地调 onPartitionsRevoked/Assigned 回调 → 下一次心跳 ACKNOWLEDGING → broker 确认后 STABLE。再均衡从”停整个世界”变成”服务端指派 + 客户端增量执行”。

端到端演算：3 消费者组的一次 cooperative-sticky 扩容

设组 g1 用 cooperative-sticky，topic t 6 分区，成员 C1、C2 在线（各 3 个分区），C3 启动加入。

  2. broker 的 GroupCoordinator（new 协议路径）发现成员数 2→3，计算新 target：C1→{0,1}、C2→{2,3}、C3→{4,5}，在所有成员的下一次心跳响应里返回各自 target；
  3. C1 收到 target：当前持有 {0,1,2}，需撤销 {2} → 状态 RECONCILING，触发用户 onPartitionsRevoked([t-2]) 回调，用户处理后 C1 把分区 {2} 从本地移除、position 清理，状态 → ACKNOWLEDGING，下一次心跳带上”已收敛到 {0,1} 且已消费完移交点”；
  4. C2 同理撤销 {3}；C3 拿到 {4,5}（新分区无已提交位移，按 auto.offset.reset=earliest 或最新提交位移初始化 position）；
  5. broker 收到三方 ACKNOWLEDGING 且与 target 一致 → 组状态 STABLE，各成员心跳响应恢复”无变化”；
  6. 全程只有分区 2、3 经历”撤销-移交”，分区 0、1、4、5 的消费从未停顿——这正是 cooperative 相对 eager 的核心价值（eager 下三个成员会同时撤销全部 6 个分区再重新分配）。

第六讲小结：把组状态和事务状态都变成日志记录

MemberState 五态：UNSUBSCRIBED → JOINING → RECONCILING → ACKNOWLEDGING → STABLE。 31. range 分配：同 topic 连续分片、余数给排序靠前者，跨 topic 可能倾斜。 32. cooperative 只撤销待移动分区；eager 每次全撤全分。

Prepare 状态是崩溃恢复锚点：重启后必须补发未写完的 marker。 38. pid fence = epoch 单调递增，旧 producer 一切请求收 PRODUCER_FENCED。 39. 事务位移（TxnOffsetCommit）以挂起态进 offsets 日志，marker 落定才转正——这就是 consume-transform-produce 原子性的来源。
