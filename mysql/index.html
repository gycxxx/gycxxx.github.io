速览：六讲各自做了什么（先看这个再进细节）

如果只读一张表就要看懂 MySQL，就是这张。六讲是一条数据流的六个接力棒——客户端字节流进来，逐棒加工，最后变成结果字节流回去或落盘。下面每行一句话讲清这棒在干嘛、接到什么、交出什么。

讲一句话白话接到什么（输入）交出什么（输出）这棒最怕什么
第一讲·启动与连接mysqld 进程”开店营业”：备齐家当→开监听门→每来个连接派一个服务员（OS 线程）专职伺候、服务完打盹等下一个OS 分配的一个 TCP/socket 连接一个带着握手认证、能收发字节包的 THD 会话家当没备齐就开门（比如引擎想写日志时日志还没起来）；连接洪峰压垮进程
第二讲·查询生命周期一条 SQL 从字节包进来，被拆成”这是什么命令”→“语法树”→“可执行对象”→跑出结果行→打包成回包THD 里那条还没解析的 SQL 字节结果集字节包（OK/结果行/ERROR）SQL 解析失败、权限不够、表不存在
第三讲·优化器拿到”要查什么”的逻辑计划，决定”用哪个索引、几张表谁先扫谁后扫、怎么连”凑出代价最小的执行计划树一个还没定怎么执行的 Sql_cmd_dml（逻辑计划）一棵 AccessPath 树 + RowIterator 执行器选错索引/选错连接顺序 → 慢几十倍
第四讲·InnoDB 引擎执行器要读/改磁盘上的行时，这一棒负责：经 buffer pool 取页→B+ 树下降找记录→改→把页改动攒进 mtrhandler 接口的一组”读这行/改这行”请求页内的行数据（读）或被改脏的页（写，挂在 flush list 等刷盘）buffer pool 抖动、页分裂、double write 没起导致页损坏
第五讲·事务·MVCC·锁多个事务同时读写时互不打架：读走 MVCC（快照 + undo 回溯不加锁）、写加锁排队、冲突就等或检测死锁一个事务要做的一串读写操作这事务的读写要么都生效要么都不生效；并发的别人看到的要么是旧版本要么阻塞死锁、脏读、不可重复读、幻读
第六讲·redo·undo·binlog·2PC一次提交怎么把”内存里改的”真正写到不丢：mtr 写 redo→引擎 prepare→binlog 落地→引擎 commit；崩了靠 redo 重放+binlog 仲裁第五讲确认要提交的事务redo/undo/binlog 都落盘的已提交事务；崩溃后能恢复到一致状态提交到一半崩了（靠 2PC 保证引擎和 binlog 不撕裂）

整本书一条线：客户端字节 → 【一·开店接客】THD → 【二·解析执行】逻辑计划 → 【三·优化器】AccessPath → 【四·InnoDB】改脏页+记redo → 【五·事务】加锁/MVCC保证并发正确 → 【六·提交恢复】2PC落盘保证不丢。

第四讲是个枢纽：读请求走到第四讲拿完行数据就可以直接回包（不经五六两讲）；只有写请求才需要继续走第五讲加锁、第六讲提交落盘。这就是为什么很多 SELECT 看起来”秒回”——它只走了前四棒。

#面试问题一句话结论深入
1MySQL 是一连接一线程吗？thread cache 是什么？默认 Per_thread_connection_handler 一连接一线程；thread cache 不是”池里的线程”，而是一群阻塞在条件变量上的线程，来连接就 signal 一个复用，服务完回到 block_until_new_connection 等下一个第一讲
28.0 的 SQL 解析入口是什么？mysql_parse 还在吗？mysql_parse() 在 8.0 已不存在；入口是 dispatch_sql_command → parse_sql → THD::sql_parser → MYSQLparse，产出 LEX 和 Sql_cmd 两个产物第二讲
3prepared statement 为什么能防注入？参数值不拼进 SQL 文本，而是用 Item_param 在 LEX 里占位、执行时才填值；这既是防注入的根本，也是”参数化查询可能拿到不同执行计划”的根源第二讲
48.0 有几套优化器？怎么共存？老优化器（贪心、只产 left-deep 树）与 hypergraph 优化器（DPhyp 枚举、支持 bushy，默认关闭）并存；两者都产出同一种中间表示 AccessPath，再由同一个 CreateIteratorFromAccessPath 统一变 RowIterator第三讲
5buffer pool 的结构是什么？大表扫描会冲掉热数据吗？“一个 page_hash + 五个链表”（LRU / free / flush_list / withdraw / unzip_LRU）；LRU 分 young/old 两段，且 Page_fetch::SCAN 模式不把页移到 LRU 头部，全表扫描不置顶第四讲
6聚簇索引和二级索引的区别？为什么会回表？聚簇索引的 key 是主键、叶子页存整行；二级索引叶子只存”索引列 + 主键值”不存完整行，所以通过二级索引查整行必须回表第四讲
7自增主键为什么比随机 UUID 快？页分裂前先试右兄弟，顺序插入走 to_right 分支几乎不搬数据；随机键插入方向不定，分裂时代价高得多第四讲
8double write 解决什么问题？半页写（torn page）：InnoDB 页 16KB 而磁盘通常只保证 4KB 原子写，redo 又是基于完整页的增量，页写坏一半无从修复——所以先顺序写一份完整副本，再写真正的表空间第四讲
9change buffer 缓存什么？唯一索引能用吗？只缓存非唯一二级索引的修改，等页因别的原因被读入时再 merge；唯一索引必须读页做唯一性检查，享受不到这个优化第四讲
10MVCC 的实现原理？记录带隐藏列 DB_TRX_ID + DB_ROLL_PTR 串起 undo 版本链；ReadView 在创建瞬间记下活跃事务 id 集合，changes_visible 三段判定可见性——读旧版本不加锁第五讲
11四个隔离级别分别解决什么问题？RR 怎么防幻读？默认 RR：RU 直接读最新（脏读）、RC 每条语句一个快照、RR 每事务一个快照、SERIALIZABLE 把普通 SELECT 也转成 LOCK IN SHARE MODE；RR 与 RC 的差异就在 read view 创建时机 + 是否用 GAP 锁，而 GAP/Next-Key 锁是文档原话”唯一能阻止幻读的机制”第五讲
12普通 SELECT 和 SELECT ... FOR UPDATE 的区别？普通 SELECT 走一致性读：顺 DB_ROLL_PTR 回溯 undo 找可见版本，不加锁；加锁读走 lock_clust_rec_read_check_and_lock，读最新已提交版本并加锁第五讲
13InnoDB 的锁有哪几种模式？死锁怎么检测？S/X 之上叠加四种精确模式位：Next-Key(0) / GAP(512) / REC_NOT_GAP(1024) / INSERT_INTENTION(2048)；死锁由 wait-for 图找环，挑环上 reservation_no 最大（最后加入环）的事务做 victim 回滚第五讲
14长事务有什么危害？版本链越长，一致性读回溯越慢；purge 不能清任何活跃 ReadView 还需要的版本，最老视图挡住 purge 使 history list 持续增长——而 undo 页本身也在 buffer pool 里、也要写 redo，“读历史版本”可能触发 IO第五讲
15redo / undo / binlog 三大日志的分工？redo（InnoDB，物理逻辑）保 crash-safe；undo（InnoDB，逻辑）保原子性和 MVCC 版本链；binlog（Server，逻辑）保复制和时间点恢复，并充当 2PC 的仲裁者第六讲
16两阶段提交的过程？为什么开了 binlog 就一定是 2PC？rw_ha_count > 1 才 prepare，而注册 binlog handlerton 后即使只有 InnoDB 计数也是 2；流程：InnoDB prepare（故意不 fsync redo）→ binlog flush/sync → 引擎 commit + redo fsync第六讲
17组提交怎么提速？innodb_flush_log_at_trx_commit 三值区别？binlog 侧 Commit_stage_manager 每阶段由 leader 攒批一次 fsync，redo 侧 log_write_up_to “推进到某个 LSN”让并发提交自然合并；三值：1=每次提交 write+fsync，2=只 write、fsync 交后台每秒一次，0=write 和 fsync 都交后台第六讲
18崩溃恢复的流程？binlog 起什么作用？重放 redo（定位 checkpoint → scan → apply）→ trx_resurrect 按 undo 标记复活未决事务 → binlog 收集 XID 由 ha_recover 仲裁：有 XID 则提交，否则回滚；且 redo fsync 必须在 binlog fsync 之后，反了会出现”redo 已提交但 binlog 没有”，从库丢事务第六讲
19char 和 varchar 的区别？char 定长：写入右补空格、读出再去尾部空格，不怕碎片；varchar 变长：行内存 1~2 字节长度前缀，省空间但更新容易页分裂/行迁移。定长内容（hash、UUID、状态码）用 char，不定长文本用 varchar——会不会溢出看行格式不看列长度，DYNAMIC 下超长部分整体走溢出页第三讲
20InnoDB 和 MyISAM 有什么区别？InnoDB：数据即聚簇索引（挂在主键上）、行级锁、MVCC、事务、外键、redo 崩溃恢复；MyISAM：数据/索引分离的堆表、表级锁、无事务无 MVCC、但 count(*) 有 O(1) 计数器、全文索引老牌。5.5 起默认存储引擎就是 InnoDB，MyISAM 只剩历史遗留和极少数只读场景第三/五讲
21MySQL 深度分页如何优化？LIMIT 100000, 10 要先把前 10 万行捞出来再丢掉，成本在”搬”不在”找”。三板斧：①延迟关联——子查询先走覆盖索引只取主键，再回表拿整行；②游标分页——WHERE id > 上一页最大id LIMIT n，把”跳过 N 行”变成”从定位点往后读”；③业务改版成”加载更多/滚动翻页”。索引解决定位，解决不了搬运第四讲
22唯一索引和主键索引的区别？主键：一表一个、聚簇索引（叶子即整行）、绝不接受 null；唯一索引：一表可多个、二级索引（叶子存”索引列+主键”）、允许多个 null（null != null 不判重）。代价上唯一索引还多一笔”必须读页做唯一性检查”，所以 change buffer 救不了它（只缓存非唯一二级索引修改）第三/四讲
23count(1)、count(*) 与 count(列名) 的区别？count(*) 与 count(1) 等价：不取值，优化器挑成本最低的索引扫行数；count(列名) 只统计该列非 null 的行，必须把值读出来判断；count(主键) 走聚簇索引。InnoDB 没有 MyISAM 那种 O(1) 计数器，哪种都是扫索引——大表统计要靠 information_schema 估算或离线数第四讲
24InnoDB 中索引类型有哪些？按结构分：B+ 树索引（聚簇 + 二级）、AHI 自适应哈希索引（自动给稳定的等值查询前缀建，btr_ahi_parts 分区锁保护，不是全表哈希）；按功能分：主键索引、唯一索引、普通索引、联合索引（最左前缀）、前缀索引、覆盖索引、全文/空间索引。默认战场是 B+ 树第三/四讲
25truncate、delete、drop 的区别？delete：逐行删、记 undo/redo、可回滚、可带 WHERE、不释放空间、不动自增值；truncate：整表抹掉重建（DDL），快、不可回滚、自增计数复位、释放空间；drop：连表定义一起删。truncate/drop 都是隐式提交的 DDL，别在事务里用第三讲
26用了索引还是很慢，可能是什么原因？索引没真走：列上有函数/运算、隐式类型转换、前导模糊 LIKE '%x'；走了但代价高：回表行太多（非覆盖索引）、区分度太低（性别/状态位）、统计信息过期选错索引；SQL 写法：深分页、ORDER BY 触发 filesort、大 IN 列表；最后也可能是锁等待/IO 打满，与索引无关。先 EXPLAIN 看 type/key/rows/Extra 四列再下结论第四讲
27设计索引时应遵循哪些原则？为 WHERE/JOIN/ORDER BY 的高频组合服务而不是越多越好：区分度高的列放联合索引前置、利用覆盖索引避免回表、控制索引数量（每个索引都是写放大 + 优化器选错概率）、长列用前缀索引、删除冗余与从未用过的索引、表结构变更后及时 ANALYZE TABLE 刷新统计信息第三/四讲
28什么是最左前缀匹配？为什么要遵守？联合索引 (a,b,c) 的 B+ 树按 a→b→c 的字典序组织，只有查询从最左列开始且不跳列，后面的列才能借排序结构收敛范围；缺了 a（或中间断档），MySQL 只能用到部分索引甚至退化为全扫/哈希过滤。“遵守”不是规矩而是 B+ 树的物理事实——索引列顺序设计错了，建了也白建第四讲
29乐观锁与悲观锁怎么实现？悲观锁假设一定冲突：SELECT ... FOR UPDATE（next-key lock 锁范围，RR 下防幻读）或应用层互斥，冲突多的时候少做无畏重试；乐观锁假设基本不冲突：加 version 列或时间戳，UPDATE ... SET v=v+1, version=version+1 WHERE id=? AND version=?，影响行数为 0 就说明被改过、走重试/失败分支，读多写少时吞吐远高于锁第五讲
30InnoDB 的表级锁、页级锁、行级锁？行级锁是逻辑的：记录锁（锁单行）、间隙锁 gap（锁”行与行之间”防幻读，仅 RR）、next-key（记录 + 左开右闭间隙）；表级有意向锁 IS/IX（行锁意图登记，让表锁判断”有没有行锁”不用全表扫）和 MDL 元数据锁（DDL 与读写互斥）；页级只是 InnoDB 内部结构锁（如 AHI 分区锁），不是用户可选的粒度第五讲
31InnoDB 加索引，这个时候会锁表吗？5.6 起是 Online DDL：默认 ALGORITHM=INPLACE 允许并发 DML，只在”准备/提交”两个极短点拿排他元数据锁；ALGORITHM=COPY 才整表重建阻塞写，LOCK 子句还能再收并发度。所以加索引不等于锁表——但大表 INPLACE 期间有主从延迟与 IO 压力，稳妥做法仍是低峰执行或 pt-osc/gh-ost 这类无锁变更工具第三讲

易错点与面试坑

以下都是文档里明确强调过的反直觉点。每条先给”坑”，再给”文档里的正解”——面试答反了比不答更糟。

  • thread cache 不是线程池。坑：答成”线程池里放着一群空闲线程等着被挑”。 正解：文档原话是”一群线程阻塞在条件变量上”，cache 的本体是 handle_connection 的 for(;;)——同一个 OS 线程依次服务多个连接，中间只 delete thd 不退出；thread_cache_size 缩容靠 shrink_cache 标志逐个 signal 让多余线程退出。
  • 别按 5.7 的记忆 grep 8.0。坑：张嘴就是 mysql_parse()、sql/opt_range.cc。 正解：前者在 8.0 已不存在（入口是 dispatch_sql_command → parse_sql → THD::sql_parser），后者拆成了 sql/range_optimizer/ 30 个文件；而 sql/sql_optimizer.cc 仍然存在且仍是老优化器主体（11830 行）——“没了的”和”还在的”都反直觉。
  • Cost_estimate 的位置和口径都容易记错。坑：说它在 sql/opt_costmodel.h，或者说 total_cost() 含内存代价。 正解：它定义在 sql/handler.h，total_cost() = io + cpu + import，不含 mem_cost；所有常量归一化到”读一个随机页 = 1.0”（DISK_SEEK_BASE_COST=0.9 + DISK_SEEK_PROP_COST=0.1/128）。
  • RR 解决幻读靠的是锁，不是快照读。坑：说”RR 的快照读解决了幻读”。 正解：文档原话——GAP/Next-Key 锁是”唯一能阻止幻读的机制”；还有隐藏细节：删除记录时 GAP 锁必须继承给下一条记录，否则删除造成的间隙失去保护，幻读照样发生。
  • double write 防的是”半页写”，不是”页写错”。坑：答成”防止页损坏”或”给 redo 做备份”。 正解：16KB 页 vs 4KB 原子写，掉电写一半时 redo 无从下手（redo 是相对完整页的增量）；所以先顺序写一份完整副本到 dblwr 文件再写真正的表空间，坏页从副本还原。
  • 行溢出看行格式，不是只看 varchar 长度。坑：以为”varchar 够长就一定溢出、不够长就一定不溢出”。 正解：COMPACT 在行内留前 768 字节 + 20 字节指针，DYNAMIC 只留 20 字节指针、整列进溢出页；TEXT/BLOB 列多的表选 DYNAMIC（8.0 默认），一行能装下的东西完全不同。
  • change buffer 和 AHI 都有适用边界。坑：以为”所有二级索引改动都能被 change buffer 缓存""InnoDB 会给热表建哈希”。 正解：change buffer 只缓存非唯一二级索引的修改（唯一索引必须读页做唯一性检查）；AHI 按”稳定的等值查询模式”自动建，不是全表建哈希，范围查询受益有限。
  • autocommit=1 时每条 DML 都是一次完整 2PC。坑：以为”一条语句谈不上事务协议”。 正解：语句执行自带隐式提交，开了 binlog 就是一次 prepare + binlog fsync + 引擎 commit + redo fsync——语句级没有”批”可言，组提交的”批”是并发事务攒出来的。
  • sync_binlog=1 不只是性能选项。坑：只把它当 durability/性能开关。 正解：崩溃后 binlog 里有没有 XID，直接决定未决事务提交还是回滚（binlog 是最终真相源）；配 innodb_flush_log_at_trx_commit=1 才是文档端到端演算里的”双 1”组合，后者取 2 表示 fsync 交后台每秒一次、取 0 表示连 write 都交后台——提交返回时数据并未落盘。
  • 长事务的危害要说出物理链条。坑：只会背”长事务会堵 purge”。 正解：undo 页本身也在 buffer pool 中、也要走 mtr、也要写 redo，版本链越长一致性读回溯越慢；同时 purge 被最老 ReadView 挡住，history list 持续增长，undo 表空间只涨不消——这是一条完整的性能雪崩链。

第一讲：mysqld 启动与连接线程模型

先说人话：本讲每个阶段在干什么

把 mysqld 想象成一家餐厅开门营业：先在后厨把水电、账本、供货商（日志、权限、存储引擎）备齐，然后才挂”营业中”的牌子开大门（监听 socket）；每来一位客人就安排一位服务员（OS 线程）专门伺候，服务员送走客人不下班，而是站在原地打盹等下一位（thread cache）。本讲就看这家店”怎么开门、怎么接客、服务员怎么复用”。

阶段/组件它干了什么（白话）为什么需要它（白话）
mysqld_main 初始化一条线跑完：先日志/权限，再引擎/数据字典，最后开监听顺序错了会出怪事：引擎想记日志时日志还没起来
连接数闸门accept 后先查 max_connections，超了直接拒绝防止连接洪峰把进程压垮
thread cache空闲线程阻塞在条件变量上，来连接就唤醒一个接客省掉每次连接都付一次建线程的成本
handle_connection一个线程的 for(;;)：握手→命令循环→收尾→回缓存线程复用的本体：服务完不退出
握手与认证验用户名密码（默认 caching_sha2 插件）得确认”来的是谁、让不让他进”

定位

这一讲回答两个问题：mysqld 这个进程是怎么从 main() 走到”能接客”的，以及一个客户端连接进来后，到底谁在伺候它。

thread cache 的真相就在这里：所谓 cache 并不是一群线程在池里等着被挑，而是一群线程阻塞在条件变量上。看 sql/conn_handler/connection_handler_per_thread.cc:381：

bool Per_thread_connection_handler::check_idle_thread_and_enqueue_connection(
    Channel_info *channel_info) {
  bool res = true;

  mysql_mutex_lock(&LOCK_thread_cache);
  if (Per_thread_connection_handler::blocked_pthread_count > wake_pthread) {
    waiting_channel_info_list->push_back(channel_info);
    wake_pthread++;
    mysql_cond_signal(&COND_thread_cache);
    res = false;
  }
  mysql_mutex_unlock(&LOCK_thread_cache);

  return res;
}

只要 blocked_pthread_count > wake_pthread（有线程正阻塞在 cache 里、且还没被叫醒），就把 Channel_info 塞进 waiting_channel_info_list 并 signal 一个线程，返回 false 表示”不用创建新线程”。对应的等待端是 sql/conn_handler/connection_handler_per_thread.cc:144 的 block_until_new_connection()，它把 blocked_pthread_count++ 然后 mysql_cond_wait，被唤醒后从 waiting_channel_info_list 里 pop_front() 拿走连接（第 171–173 行）。

thread_cache_size 的动态调整在 sql/conn_handler/connection_handler_per_thread.cc:354 的 modify_thread_cache_size()：cache 要缩小时置 shrink_cache = true，用 mysql_cond_signal 逐个叫醒多余的线程让它们退出，然后等 COND_flush_thread_cache 直到 blocked_pthread_count 降到目标值。

3.2 make_join_plan：贪心 + 深度剪枝

sql/sql_optimizer.cc:5308。名字叫”plan”，实际是经典的 MySQL greedy search：

  • 用 greedy_search() 逐层扩展 join 前缀（第 1 张表 → 前 2 张 → …），每层用 best_extension_by_limited_search() 在剩余表里挑最优；
  • 搜索深度受 optimizer_search_depth 控制（0 = 自动）；超过阈值退化为纯贪心；
  • 每个候选的代价由 POSITION 累加 Cost_estimate。

老优化器只考虑左深树（left-deep），这是它与 hypergraph 最本质的区别——hypergraph 能做 bushy tree 和星型/雪花型。

第四讲：InnoDB 存储引擎 —— buffer pool、B+ 树与行格式

先说人话：本讲每个阶段在干什么

4.5 double write：为什么要写两遍

Double_write 类在 storage/innobase/buf/buf0dblwr.cc:430。要解决的问题：InnoDB 页 16KB，而磁盘/文件系统通常只保证 4KB 原子写；写一半掉电就产生”半页写（torn page）“，redo 也无法修复（redo 是基于完整页做增量）。

解法是”先顺序写一份到 double write buffer，再写真正的数据文件”：

  • Double_write::prepare（storage/innobase/buf/buf0dblwr.cc:1305）把页拷进 dblwr 的 batch buffer；
  • Double_write::write_dblwr_pages（storage/innobase/buf/buf0dblwr.cc:2160）把 batch 顺序写到 #innodb_dblwr 文件并 fsync；
  • Double_write::write_data_pages（storage/innobase/buf/buf0dblwr.cc:2192）再把页写到真正的表空间；
  • 若某页写坏了，从 dblwr 文件还原：is_dblwr_page_corrupted（storage/innobase/buf/buf0dblwr.cc:2927）判断、Double_write::write_to_datafile（:1603）负责回写。

8.0.46 里还有精简版 double write（Reduced_double_write::allocate，storage/innobase/buf/buf0dblwr.cc:1200）与原子写探测（若设备支持 16KB 原子写则跳过 dblwr，见 storage/innobase/buf/buf0dblwr.cc:830 的 “Atomic write enabled” 日志）。

4.10 change buffer

ibuf_insert（storage/innobase/ibuf/ibuf0ibuf.cc:3283）→ ibuf_insert_low（:2978）。

解决的问题：二级索引页不在 buffer pool 时，为了做一次 INSERT/DELETE-MARK 而把页读进来，代价很高。change buffer 把”对二级索引的修改”缓存下来（存在 ibuf 自己的 B+ 树里，位于系统表空间），等该页因为别的原因被读入时再 merge 进去。

  2. 分裂前先试右兄弟、分裂方向由 direction 决定：btr_page_split_and_insert 第一步是 btr_insert_into_right_sibling（storage/innobase/btr/btr0btr.cc:2348），顺序插入走 btr_page_get_split_rec_to_right（:1677）分支几乎不搬数据——这解释了为什么自增主键的插入性能远好于随机 UUID。
  3. double write 解决的是”半页写”，不是”页写错”：redo 是相对完整页的增量，页被写坏一半时 redo 无从下手，所以必须先有一份完整的副本。实现见 Double_write::write_dblwr_pages（storage/innobase/buf/buf0dblwr.cc:2160）→ write_data_pages（:2192）。

第五讲：事务、MVCC 与锁

先说人话：本讲每个阶段在干什么

MVCC 像共享文档的”历史版本”功能：每次改动都把旧内容存档（undo 版本链），每个人打开文档时拍一张”此刻谁还在改”的快照（ReadView），各看各的定稿、互不打扰也不用排队（读不加锁）。而”锁”就是编辑权本身：谁在改哪一段、连空位（间隙）归谁管都有精确规矩；起了环路争执，还有裁判（死锁检测）当场裁掉一个。

定位

这一讲把三条线拧在一起：

  1. 事务状态机（trx0trx.cc）：一个 trx_t 从 NOT_STARTED 走到 COMMITTED_IN_MEMORY；
  2. MVCC（read/read0read.cc + trx/trx0rec.cc + row/row0vers.cc）：靠 ReadView + undo 版本链实现”读不加锁”；

5.2 ReadView 与 MVCC

ReadView::prepare（storage/innobase/read/read0read.cc:447）：

void ReadView::prepare(trx_id_t id) {
  ut_ad(trx_sys_mutex_own());

  m_creator_trx_id = id;

  m_low_limit_no = trx_get_serialisation_min_trx_no();

  m_low_limit_id = trx_sys_get_next_trx_id_or_no();

  ut_a(m_low_limit_no <= m_low_limit_id);

  if (!trx_sys->rw_trx_ids.empty()) {
    copy_trx_ids(trx_sys->rw_trx_ids);
  } else {
    m_ids.clear();
  }

  /* The first active transaction has the smallest id. */
  m_up_limit_id = !m_ids.empty() ? m_ids.front() : m_low_limit_id;

  ut_a(m_up_limit_id <= m_low_limit_id);

  ut_d(m_view_low_limit_no = m_low_limit_no);
  m_closed = false;

四个字段的含义：

  • m_low_limit_id = 创建视图时”下一个还没分配的 trx id”，>= 它的修改一律不可见；
  • m_up_limit_id = 活跃事务里最小的 id，< 它的修改一律可见；
  • m_ids = 创建视图时还活着的读写事务 id 列表（有序，供二分）；
  • m_low_limit_no = 当前最小未提交事务的 trx no，purge 用它判断”能不能删”。

可见性判断 storage/innobase/include/read0types.h:163：

  [[nodiscard]] bool changes_visible(trx_id_t id,

5.3 undo 版本链与一致性读

一条记录被更新时，旧版本写进 undo：trx_undo_report_row_operation（storage/innobase/trx/trx0rec.cc:2120）→ 插入走 trx_undo_page_report_insert（:481）、更新走 trx_undo_page_report_modify（:1152）。记录里的 DB_ROLL_PTR 指向这个 undo 记录。

回滚指针的另一半是 trx_undo_prev_version_build（storage/innobase/trx/trx0rec.cc:2450）——从当前记录 + undo 记录”重建”出上一个版本。

一致性读的完整回溯在 row_vers_build_for_consistent_read（storage/innobase/row/row0vers.cc:1249）：顺着 DB_ROLL_PTR 一路往前，直到找到一个 changes_visible() 为 true 的版本，或者版本链走完。

二级索引的一致性读要特殊处理：row_vers_old_has_index_entry（storage/innobase/row/row0vers.cc:974）判断”历史上这个二级索引项是否曾经存在”，因为二级索引记录没有 trx_id/roll_ptr。

关键事实：undo 存在于 rollback segment 里，而 undo 页本身也在 buffer pool 中、也要走 mtr、也要写 redo。所以”读历史版本”可能触发 IO。这就是长事务导致性能雪崩的物理原因——版本链越长，一致性读回溯越慢。

5.4 purge

trx_purge（storage/innobase/trx/trx0purge.cc:2390）由后台 purge 线程循环调用（trx_purge_run，storage/innobase/trx/trx0purge.cc:2574）。一次 purge 的流程：

  1. trx_purge_choose_next_log（storage/innobase/trx/trx0purge.cc:1864）选下一个要处理的 undo log（按 history list 的 trx no 升序，保证顺序）；
  2. trx_purge_rseg_get_next_history_log（storage/innobase/trx/trx0purge.cc:1703）从 rseg 的 history list 取；
  3. trx_purge_attach_undo_recs（storage/innobase/trx/trx0purge.cc:2237）把 undo 记录批量分配给各个 purge worker 线程（innodb_purge_threads）；
  4. worker 侧 row_purge（storage/innobase/row/row0purge.cc:1151）→ row_purge_record（:1141）→ row_purge_parse_undo_rec（:842）解析记录类型，再决定：
    • 删除二级索引项：row_purge_poss_sec（storage/innobase/row/row0purge.cc:275）先判断这个二级索引项还是否可能被任何活跃 read view 看到；
    • 真正删除聚簇索引记录。
  5. 清理：trx_purge_truncate（storage/innobase/trx/trx0purge.cc:2375）→ trx_purge_truncate_history（:1596）→ 释放不再需要的 undo 页/段（trx_purge_free_segment，:418）。

purge 不能删的判据：purge_sys->view（最老的活跃 ReadView）的 m_low_limit_no。只要还有 read view 需要看到某版本，对应 undo 就不能清。这也是 history list length 增长的直接原因。

第六讲：redo / undo / binlog 与两阶段提交

先说人话：本讲每个阶段在干什么

提交一笔事务像银行做”双账本对账”：redo 是柜台的流水账（记每个页物理上改了什么），binlog 是给客户的对账单（记逻辑上发生了什么），undo 是改动前的旧凭证。转账前先在两本账上都标”待定”（prepare），对账单先盖钢印（binlog fsync），柜台账才落袋（redo fsync + commit）；万一中途停电，重启后拿对账单当最终裁判：单子上有这笔就确认，没有就当没发生过。

log_t管 sn/write_lsn/flushed_lsn，无锁 Link_buf 推进并发写 buffer 和落盘互不阻塞

本讲主线：mtr 把页改动写进 redo buffer → 提交：prepare（故意不 fsync）→ binlog FLUSH+SYNC 落地 → 引擎 commit + fsync redo → 万一崩溃：重放 redo + 复活事务 + binlog 仲裁提交/回滚

定位

这一讲回答”提交到底发生了什么”，以及”崩溃后凭什么能恢复”。三份日志各有分工：

  • redo（InnoDB）：物理逻辑日志，保证 crash-safe（崩溃后能把页重做到崩溃前状态）；
  • undo（InnoDB）：逻辑日志，保证原子性（回滚）和 MVCC（版本链）；
  • binlog（Server）：逻辑日志，保证复制和时间点恢复。

三者必须原子一致，靠的就是两阶段提交（2PC）。

6.1 redo 的写入：mtr 是唯一入口

mtr_t::commit（storage/innobase/mtr/mtr0mtr.cc:662）→ mtr_t::Command::execute（storage/innobase/mtr/mtr0mtr.cc:842）：

void mtr_t::Command::execute() {
  ut_ad(m_impl->m_log_mode != MTR_LOG_NONE);

  ulint len = prepare_write();

  if (len > 0) {
    mtr_write_log_t write_log;

    write_log.m_left_to_write = len;

    auto handle = log_buffer_reserve(*log_sys, len);

    write_log.m_handle = handle;
    write_log.m_lsn = handle.start_lsn;

    m_impl->m_log.for_each_block(write_log);

    ut_ad(write_log.m_left_to_write == 0);
    ut_ad(write_log.m_lsn == handle.end_lsn);

    log_wait_for_space_in_log_recent_closed(*log_sys, handle.start_lsn);

    DEBUG_SYNC_C("mtr_redo_before_add_dirty_blocks");

    log_buffer_close(*log_sys, handle);

    m_impl->m_mtr->m_commit_lsn = handle.end_lsn;

  } else {
    DEBUG_SYNC_C("mtr_noredo_before_add_dirty_blocks");

    add_dirty_blocks_to_flush_list(0, 0);
  }

  release_all();

}

四步，缺一不可：

  1. log_buffer_reserve（storage/innobase/log/log0buf.cc:859）：在 log buffer 里按 sn（不含块头的”数据字节数”）原子地预留一段空间，返回 Log_handle{start_lsn, end_lsn}；
  2. 把 redo 记录拷进 buffer（storage/innobase/log/log0buf.cc:922 的 log_buffer_write）；
  3. add_dirty_blocks_to_flush_list（mtr0mtr.cc:867）：把 mtr 改过的页按 start_lsn 挂进 flush list；
  4. log_buffer_close（storage/innobase/log/log0buf.cc:1142）：用 recent_written 这个 Link_buf 标记”这段已经写完”，让 log_writer 可以推进。

第 3 步与第 4 步的顺序是 WAL 的核心：必须先挂 flush list（页的 oldest_modification = start_lsn），再宣布 redo 可写。反过来就会出现”redo 写了但页没标记脏”，崩溃后页丢失修改。

6.3 group commit 在 InnoDB 侧

mtr 提交只保证”redo 进了 buffer”。真正决定”落盘时机”的是提交时的 log_write_up_to：

  • innodb_flush_log_at_trx_commit = 1：每次提交都 write + fsync（log_write_up_to(..., true)）；
  • = 2：每次提交只 write，fsync 交给后台每秒一次；
  • = 0：write 和 fsync 都交给后台。

mtr0mtr.cc:1240 就是 log_write_up_to(*log_sys, commit_lsn(), true) 这一行的位置。由于 log_write_up_to 是”推进到某个 LSN”，并发提交会自然合并成一次 fsync —— 这就是 redo group commit。

6.4 undo

undo 的组织：trx_t → trx_rseg_t（rollback segment，storage/innobase/trx/trx0rseg.cc）→ trx_undo_t（undo log）→ undo 页。

8.0 的 undo 放在独立的 undo tablespace（undo_001、undo_002，可 CREATE UNDO TABLESPACE）。rollback segment 数量由 innodb_rollback_segments 控制，其中一部分固定给临时表（noredo rseg，见 trx0trx.cc:3024 对 trx->rsegs.m_noredo 的处理）。

undo 分两类：

  • insert undo：只用于回滚，事务提交后立即可以丢弃（因为没有 read view 需要看到”插入前的空”）；
  • update undo：还要服务 MVCC，提交后挂进 history list 等 purge（trx_purge_add_update_undo_to_history，storage/innobase/trx/trx0purge.cc:317）。

三个最值得记住的点：

  5. 代价尺度归一化：平均一次随机读页 = 1.0，DISK_SEEK_BASE_COST=0.9 + DISK_SEEK_PROP_COST=0.1/128。
  6. AccessPath 在 sql/join_optimizer/access_path.h:193，CreateIteratorFromAccessPath 在同文件 :1722。
  7. 直方图两种：SINGLETON（低基数）/ EQUI_HEIGHT（高基数），选择率接口 get_selectivity（sql/histograms/histogram.h:660）。
  8. 8.0 已移除 query cache（本仓库 sql/ 下无 sql_cache.cc 等相关文件）。

InnoDB 存储：

  1. buffer pool = 1 个 page_hash + 5 个链表：LRU / free / flush_list / withdraw / unzip_LRU（buf0buf.h:2405/2382/2335/2387/2420）。
  2. Page_fetch::SCAN 不把页移到 LRU 头 —— 防大扫描冲掉热数据。
  3. 页分裂先试右兄弟；顺序插入走 btr_page_get_split_rec_to_right 分支几乎不搬数据。
  4. DYNAMIC vs COMPACT 的本质是溢出列处理：COMPACT 留前 768 字节，DYNAMIC 只留 20 字节指针。
  5. 隐藏列 DB_TRX_ID + DB_ROLL_PTR 是 MVCC 的物理载体。
  6. double write 解决”半页写”，不是”页写错”；先顺序写 dblwr 文件，再写表空间。
  7. change buffer 只缓存非唯一二级索引的修改；唯一索引必须读页做唯一性检查。
  8. AHI 按查询模式自动建，只有稳定的等值查询前缀受益。

事务 / MVCC / 锁：

  1. 事务状态：NOT_STARTED → ACTIVE → (PREPARED) → COMMITTED_IN_MEMORY（trx0trx.h:742–746）。
  2. trx_commit_low 里的 mtr_commit(mtr) 一行（trx0trx.cc:2224）就是”事务在文件世界里提交”的那一刻。
  3. changes_visible 只有三段判定：id < m_up_limit_id 或 id == 自己 → 可见；id >= m_low_limit_id → 不可见；中间二分查 m_ids（read0types.h:163）。
  4. m_ids 有序才能二分 —— 这是 ReadView::prepare 要 copy_trx_ids 的原因。
  5. RC 与 RR 的两条差异：read view 创建时机（每语句 vs 每事务）+ 是否用 GAP 锁（skip_gap_locks()，trx0trx.h:1113）。
  6. 四种精确模式位：LOCK_ORDINARY(0，Next-Key) / LOCK_GAP(512) / LOCK_REC_NOT_GAP(1024) / LOCK_INSERT_INTENTION(2048)。
  7. 加锁三级优化：lock_rec_lock_fast（页上只有本事务一把锁时直接改位图）/ slow / lock_rec_lock 分派。
  8. 删除记录时 GAP 锁要继承给下一条记录（lock_rec_inherit_to_gap），否则幻读防不住。
  9. 死锁检测在 lock/lock0wait.cc（不是 lock0lock.cc），victim = 环上 reservation_no 最大者。
  10. purge 不能清掉任何活跃 read view 需要的版本；判据是最老 view 的 m_low_limit_no。

redo / undo / binlog / 2PC：

  1. mtr 提交四步：log_buffer_reserve → 拷贝 → add_dirty_blocks_to_flush_list → log_buffer_close。第 3 步必须早于第 4 步。
  2. log_t 在 storage/innobase/include/log0sys.h:77；log0log.h 仍存在（382 行）但只是聚合头。
  3. recent_written / recent_closed 两个无锁 Link_buf 取代了老版本的大 mutex。
  4. flushed_to_disk_lsn 是耐久性的判据；available_for_checkpoint_lsn 是 checkpoint 的上界。
  5. prepare 阶段设 HA_IGNORE_DURABILITY（sql/binlog.cc:8051），把 redo fsync 推迟到 binlog flush 阶段批量做。
  6. ordered_commit 五阶段：Stage#0（从库顺序）→ FLUSH → SYNC → COMMIT → AFTER_COMMIT。
  7. ha_commit_trans 的 rw_ha_count > 1 判定：开了 binlog 就一定 2PC（binlog handlerton 也算一个）。
  8. redo fsync 必须在 binlog fsync 之后（sql/binlog.cc:9000 → log_write_up_to）。
  9. 恢复分两段：recv_recovery_from_checkpoint_start（扫描 + 应用 redo）→ recv_recovery_from_checkpoint_finish。
  10. trx_resurrect 按 undo 标记复活事务：commit → COMMITTED_IN_MEMORY，prepare → PREPARED，都没有 → ACTIVE（回滚）。
  11. 仲裁动作就是 sql/binlog/recovery.cc:112 的 ha_recover(&m_internal_xids, &xa_list)：binlog 里有 XID 就提交，没有就回滚。
