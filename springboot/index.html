三条主线：

  1. 启动流：SpringApplication.run —— 从 new SpringApplication（推断 Web 类型、加载 SpringFactoriesLoader 扩展）到 refreshContext + callRunners + listeners.ready 的完整生命周期，失败时 handleRunFailure 统一收口；
  2. 配置流：外部化配置（命令行参数/环境变量/application.yml）→ Environment（PropertySource 链）→ Binder（松弛绑定）→ @ConfigurationProperties Bean；自动配置候选则经 AutoConfigurationImportSelector 过滤后由条件注解逐个裁决；
  3. Web 流：onRefresh 钩子内创建内嵌容器（Servlet 栈 TomcatServletWebServerFactory、Reactive 栈 NettyReactiveWebServerFactory），initialize 与 start 两阶段分离（先建对象后绑端口），请求最终进入 DispatcherServlet。

高频 Q&A（先结论）

先结论、后细节：16 个最高频问题各配一句话，覆盖启动流、自动配置、Web 容器、外部化配置与构建生态五条主线； 回答时避免一上来就陷入实现细节，先给结论再按 深入 列回讲次展开。

#面试问题一句话结论深入
1Spring Boot 自动配置原理？候选自动配置类全部登记在 META-INF/spring/*.imports（Boot 4 核心模块仅 12 个，全仓约 100 份），AutoConfigurationImportSelector 以”加载 → 去重 → 排除 → 过滤 → 排序”五步漏斗处理，再由条件注解逐个裁决；用户 Bean 永远先注册，自动配置只做”查漏补缺”第二讲
2条件注解如何求值？FilteringSpringBootCondition 双通道：导入前读 spring-autoconfigure-metadata.properties 元数据对类名数组批量过滤（不加载类、可并行），refresh 期才真正加载类求值；OnBeanCondition 锁死 REGISTER_BEAN 阶段，这是 @ConditionalOnMissingBean 可靠性的根基第二讲
3自动配置类的加载顺序怎么定？三段论：类名字母序打底保证确定性 → @AutoConfigureOrder → @AutoConfigureBefore/After 拓扑展开（递归补齐关系类、遇环即抛异常）；全程只读 ASM 元数据，候选类不在 classpath 上也能排第二讲
4starter 机制是什么？一个 starter jar 通常零代码，全部内容就是构建脚本里的依赖声明；引入一个坐标 = 引入一组传递依赖 + 一批自动配置候选——“约定优于配置”的物理基础就是依赖传递，classpath 即配置第五讲
5如何自定义一个 starter？沿用同一约定：写一个只做依赖聚合的 jar，按需附带自动配置类并登记进 META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports（每行一个全限定名，# 为注释），用户引入即生效第五讲
6SpringApplication.run 的流程？九步流水线：推断类型 → starting → 准备 Environment → 创建 Context → prepareContext 装 Bean → refresh → started → callRunners → ready；每步经 SpringApplicationRunListener 7 个回调广播事件，任何异常统一汇入 handleRunFailure第一讲
7spring.main.* 为什么能关掉启动行为？因为 bindToSpringApplication 发生在 ConfigData 处理之后——所以 spring.main.web-application-type=none、spring.main.banner-mode=off 这些”控制启动本身”的开关才生效；配合默认属性三处 moveToEnd，“默认值永远最低优先级”是双保险第一讲
8启动失败怎么排查？失败三件套：退出码（ExitCodeExceptionMapper → ExitCodeGenerator，第一个非零胜出）+ FailureAnalyzer 人话报告（内置 18 个，Description/Action 结构）+ AbandonedRunException 静默短路；看到 “APPLICATION FAILED TO START” 先读 Action 段，它不是堆栈第一讲
9外部化配置的优先级顺序？“后来者居上”：命令行参数 addFirst 永远最高，其下是系统属性/环境变量，ConfigData addLast 进链尾，@PropertySource 反而低于 application.yml，DefaultPropertiesPropertySource 被三处 moveToEnd 永远垫底第四讲
10Profile 机制？只认 spring.profiles.active，default/group/include 都是派生量；ConfigData 两轮处理——先无 profile 拿到激活属性，再带 profile 加载 application-{profile}；休眠配置里写 include 会抛 InactiveConfigDataAccessException第四讲
11@ConfigurationProperties 与宽松绑定？装配链 @EnableConfigurationProperties → EnableConfigurationPropertiesRegistrar → ConfigurationPropertiesBindingPostProcessor → ConfigurationPropertiesBinder → Binder；max-attempts/MAX_ATTEMPTS/maxAttempts 收敛到同一 UNIFORM 规范名，绑定发生在每个 Bean 初始化前第四讲
12Binder 的绑定过程？松弛名匹配 → ${...} 占位符解析（PropertySourcesPlaceholdersResolver）→ 类型转换（ConversionService）→ setter/构造器注入 → JSR-303 校验；ignoreUnknownFields 默认 true，未知键静默忽略，设 false 才暴露拼写错误第四讲
13@SpringBootApplication 三合一注解？@SpringBootConfiguration + @EnableAutoConfiguration + @ComponentScan：主类作为 primary source 在 prepareContext 的 load 阶段进入容器，refresh 时被 ConfigurationClassPostProcessor 解析出 AutoConfigurationImportSelector，自动配置自此导入第一、二讲
14内嵌 Tomcat 启动原理？onRefresh 里从容器取唯一的 ServletWebServerFactory Bean 造出 TomcatWebServer：initialize 阶段 bindOnInit=false 只初始化不绑端口，finishRefresh 后 LifecycleProcessor 才调 start() 真正 bind——“Bean 全就绪才开放流量”，零半启动窗口第三讲
15优雅停机怎么做的？三段式：doClose 先发 REFUSING_TRAFFIC 摘流量 → WebServerGracefulShutdownLifecycle（专用 phase，早于 stop lifecycle）→ GracefulShutdown pause 连接器并每 50ms 轮询在途请求归零；server.shutdown=graceful 才开启，默认 immediate第三讲
16可执行 jar 的原理？repackage 三件事：classes 搬进 BOOT-INF/classes、依赖原样嵌进 BOOT-INF/lib/、MANIFEST 把 Main-Class 换成 JarLauncher（原主类记入 Start-Class）；java -jar 的真实入口是 loader——注册 jar:nested: 协议 → LaunchedClassLoader → 反射调 Start-Class，嵌套 jar 全程不解压第五讲

易错点与面试坑

以下都是文档中强调过的反直觉点，每一条对应一个”知道即加分、不知道就翻车”的瞬间； 按优先级排好了，前三条是源码结论与直觉冲突最厉害的地方。 每条都附了”怎么躲”：改法或排障入口，直接可用。

  • @PropertySource 优先级低于 application.yml（最反直觉的一条）：前者 refresh 期才加入、后者 addLast 在前，链式语义”后来者居上”； 想让 @PropertySource 赢，需要它 addFirst 或改用 ConfigData import。 这也是”我把配置从 yml 挪到注解里为什么不生效”这类问题的标准答案。
  • 同一位置 .properties 优先于 .yaml：loader 顺序是 [Properties, Yaml]，倒序插入后 properties 后被应用，官方结论代码可印证； 同一目录混排两种格式时，这是个典型的暗坑。
  • 自动配置顺序会”静默跳过”：@AutoConfigureBefore/After 指向的关系类不可用时直接跳过不报错，只有检测到环才抛 “AutoConfigure cycle detected”； 顺序写错可能无声无息，排障时打开 --debug 的条件评估报告。
  • @ConditionalOnBean 顺序敏感：OnBeanCondition 在 REGISTER_BEAN 阶段只统计”将要注册”的 Bean 定义，自动配置之间并不真正互相注入； 用户代码里写 @ConditionalOnBean 要警惕顺序，@ConditionalOnMissingBean 才是自动配置的正确姿势。
  • 排除项写错类名会炸启动：spring.autoconfigure.exclude 排一个不在候选中的类直接抛 IllegalStateException（防拼写错误静默失效）； spring.boot.enableautoconfiguration=false 则是整体关闭自动配置的总开关。
  • ignoreUnknownFields 默认 true：yml 里多写的键被静默忽略，设 false 才抛 UnboundConfigurationPropertiesException； 排查”值怎么没绑上”先看 Origin——OriginTrackedMapPropertySource 记录每个值来自哪个文件哪一行。
  • 端口冲突报错发生在启动末端：bindOnInit=false + START_EVENT 摘除 connector，使 tomcat.start() 只初始化不监听，报错推迟到 LifecycleProcessor.start； server.port=0 时真实端口从 connector.getLocalPort() 取并回填 local.server.port。
  • 内嵌容器与外部容器的分界：一旦定义任何 ServletContextInitializer Bean，自动注册 Servlet/Filter 的行为就关闭（防双注册）； Boot 4 里 spring-boot-starter-web 已 deprecated、Undertow 支持被移除，换容器 = 换 -runtime starter，编译期零改动。 同一个容器里出现两个 ServletWebServerFactory Bean 会直接抛异常，排障时先查依赖树。

第一讲：SpringApplication.run —— 一次启动的全流程

定位

SpringApplication 是 Spring Boot 的”总装配线”：它把一个普通的 main 方法编排成「推断环境 → 准备 Environment → 创建 ApplicationContext → 加载 Bean 定义 → refresh → 回调 Runner」的标准流水线，并把每一步通过 SpringApplicationRunListener 事件暴露给扩展方。理解这一个类（1876 行）的 run(String...) 方法，就理解了 Spring Boot 应用 90% 的启动行为。本讲所有行号均对应 core/spring-boot/src/main/java/org/springframework/boot/SpringApplication.java。

  3. 失败路径三件套：退出码（ExitCodeExceptionMapper → ExitCodeGenerator，第一个非零胜出）、FailureAnalyzer 报告（18 个内置分析器，输出 Description/Action 结构）、AbandonedRunException 静默退出短路——排查”APPLICATION FAILED TO START”时先看 Action 段，它由具体 FailureAnalyzer 生成而非堆栈。

第二讲：自动配置 —— @EnableAutoConfiguration 与条件注解家族

定位

自动配置要回答一个问题：classpath 上有什么，用户就最可能需要什么 Bean。Spring Boot 的答案是：所有”候选自动配置类”登记在 META-INF/spring/*.imports 文件里，@EnableAutoConfiguration 通过 AutoConfigurationImportSelector（一个 DeferredImportSelector）把它们全部导入，再用条件注解家族逐个裁决”当前环境是否匹配”，匹配的才成为真正的 Bean 定义。本讲所有路径相对仓库根；Boot 4 中该机制核心位于 core/spring-boot-autoconfigure（条件注解）与 core/spring-boot（context/annotation/ImportCandidates、Binder）。

StandardConfigDataLocationResolver（context/config/StandardConfigDataLocationResolver.java:59）：

  • CONFIG_NAME_PROPERTY = "spring.config.name"，默认 {"application"}（L65–67，可多名字：spring.config.name=app,myapp）；
  • resolve（L118–147）区分目录与文件：目录展开为 getReferencesForDirectory（L191–199，对每个 configName × 每个 loader 的每个扩展名生成引用），getReferencesForConfigName（L201–214）用 addFirst 倒序插入——loaders 顺序是 [Properties, Yaml]（spring.factories），最终 deque 头是 yaml、尾是 properties，properties 后被应用故优先级更高（官方文档：“同一位置 .properties 优先于 YAML”，documentation/spring-boot-docs/src/docs/antora/modules/reference/pages/features/external-config.adoc:42）；

starter 组成约定：只聚合，不实现

starter 的约定是：一个 starter jar 里通常没有任何代码，它的全部内容就是一份构建脚本里的依赖声明。以核心 starter 为例（starter/spring-boot-starter/build.gradle）：

plugins { id "org.springframework.boot.starter" }
description = "Core starter, including auto-configuration support, logging and YAML"
dependencies {
    api(project(":starter:spring-boot-starter-logging"))
    api(project(":core:spring-boot-autoconfigure"))
    api("jakarta.annotation:jakarta.annotation-api")
    api("org.yaml:snakeyaml")
}

即：spring-boot-starter = 日志（logback 默认）+ autoconfigure 模块（携带全部 .imports 候选）+ yaml 解析器。用户 引入 spring-boot-starter 的瞬间，classpath 上就有了全部自动配置候选——“约定优于配置”的物理基础就是依赖传递。

  1. 协议注册（L58）：Handlers.register() 装上 Boot 自研的 jar 协议处理器——之后 jar:nested:/app.jar/BOOT-INF/lib/xxx.jar!/ 这类”jar 中的 jar”URL 可被 URLConnection 直接读取（loader/net/protocol/），无需解压；
  2. ClassLoader（L81–88）：new LaunchedClassLoader(isExploded(), getArchive(), urls, parent)——classpath URL 来自 getClassPathUrls()（JarFileArchive 遍历，isLibraryFileOrClassesDirectory L183–189：BOOT-INF/classes/ 与 BOOT-INF/lib/* 才入链，顺序即优先级）；
  3. main 反射调用（L97–108）：设置 TCCL 为 LaunchedClassLoader，Class.forName(mainClassName, false, classLoader)——此时才触发应用主类及其依赖的加载（此前只有 loader 类被加载）；getMainClass() 从 MANIFEST 读 Start-Class（即用户的 com.example.MyApplication）；
  4. 之后就是第一讲的 SpringApplication.run 全流程。

java -Djarmode=tools -jar app.jar 则把主类换成 JarModeRunner（L62–63），提供 classpath/layertools 等维护工具（loader/spring-boot-jarmode-tools）。

actuator 简述

Boot 4 的 actuator 拆成两个模块：module/spring-boot-actuator（endpoint 基础设施）与 module/spring-boot-actuator-autoconfigure（自动配置，imports 登记 EndpointAutoConfiguration、HealthEndpointAutoConfiguration 等一批）。核心抽象在 module/spring-boot-actuator/src/main/java/org/springframework/boot/actuate/endpoint/：ExposableEndpoint/Operation（一个 endpoint 多个操作）、EndpointId（URL 段）、Access（READ/WRITE/NONE）+ EndpointAccessResolver（与 Spring Security 集成做权限）、EndpointsSupplier（收集）。技术模块再各自贡献端点（module/spring-boot-tomcat 的 actuate/web/server/TomcatServletManagementContextAutoConfiguration 支持独立管理端 child context）。引入 spring-boot-starter-actuator 即获得 /actuator/health、/env、/beans、/conditions（第二讲 ConditionEvaluationReport 的出口）、/configprops 等——排障三板斧全在这里。

Boot 4 新特性速览（均有源码/文档印证）

  1. 模块扁平化重构：Boot 3 的 spring-boot-project/* 全部拆散为顶层 core/、module/（~110 个技术模块）、starter/、loader/、build-plugin/、platform/（见 settings.gradle）；spring-boot-autoconfigure 核心只剩 12 个候选，其余按技术栈下沉——“引什么starter才有什么自动配置”成为硬边界；
  2. Web 服务器独立：org.springframework.boot.web.server 全族迁入 module/spring-boot-web-server；Undertow 支持移除（settings.gradle 无 undertow 模块）；
  3. WebApplicationType 推断 SPI 化：deduce() 改走 Deducer SPI（WebApplicationType.java:63–71，@since 4.0.1），Reactive 判定由 webflux 模块提供，核心模块不再硬依赖 spring-web；
  4. starter compile/runtime 拆分：spring-boot-starter-tomcat-runtime 等 -runtime starter 把容器依赖移到运行期（transitive=false），spring-boot-starter-web deprecated → webmvc/webflux；
  5. CRaC 一等公民：Startup.create() 自动检测 CRaC MXBean 切换”Restored”语义（SpringApplication.java:1771–1776），新增 @ConditionalOnCheckpointRestore；
  6. 版本基线：gradle.properties：version=4.1.1、springFrameworkVersion=7.0.9、tomcatVersion=11.0.24、graalVersion=25；系统要求”至少 Java 17、最高兼容 Java 26”（documentation/spring-boot-docs/src/docs/antora/modules/ROOT/pages/system-requirements.adoc:4）；native image 需 JDK 25（SpringApplication.NativeImageRequirementsException L1655–1673，MINIMUM_REQUIRED_JAVA_VERSION = JavaVersion.TWENTY_FIVE）；AOT Cache 需 Java 25+（documentation/.../packaging/aot-cache.adoc:17）；
  7. API 演进信号：prepareContext(Host, ServletContextInitializer[], TempDirs) 取代旧签名（@since 4.1.0，旧方法标 forRemoval since 4.1.0，TomcatServletWebServerFactory.java:174–180）——4.x 仍在高速迭代，升级时注意 deprecation 警告。

第五讲小结：starter 管依赖约定，repackage 管结构，loader 管加载

一句话定位：starter 用”纯依赖聚合”实现约定优于配置（Boot 4 再把容器拆成 compile/runtime 两个 starter）；spring-boot-maven-plugin 的 repackage 把普通 jar 改写成 BOOT-INF/classes + BOOT-INF/lib/* 结构并把 MANIFEST 的 Main-Class 换成 JarLauncher；运行时 Launcher 注册 jar:nested: 协议、构造 LaunchedClassLoader，反射调用 Start-Class——嵌套 jar 不解压，靠自定义 ClassLoader 直接读。

三个最值得记住的点：

  1. starter 零代码是特性不是偷懒：约定全在构建脚本里（starter/spring-boot-starter/build.gradle 五行依赖），换容器 = 换 starter（Boot 4 的 -runtime 拆分让这件事连编译期都不受影响）；自动配置候选跟着 starter 走，classpath 即配置；
  2. repackage 只做三件事：内容搬家（classes → BOOT-INF/classes、依赖 → BOOT-INF/lib/）、MANIFEST 改写（Main-Class=JarLauncher、Start-Class=原主类）、签名清理（writeSignatureFileIfNecessary 剔除旧签名文件防 SecurityException）——依赖 jar 原样嵌套不解压，这是”大应用启动也不慢”的结构前提；
  3. java -jar 的真实入口是 loader 而非你的 main：Handlers.register() 装 jar:nested: 协议 → LaunchedClassLoader 以 BOOT-INF/classes + BOOT-INF/lib/* 为 classpath → 反射调 Start-Class；排查”嵌套 jar 里读资源/ClassNotFound”问题时，先怀疑 LaunchedClassLoader 的可见性与 jar:nested: 协议是否注册（ exploded 部署不走协议注册，Launcher.java:57）。

全链路复习卡

启动流：

  1. run 九步流水线：Startup.create → getRunListeners → prepareEnvironment → prepareContext → refreshContext → afterRefresh → callRunners → listeners.ready；任一步异常都汇入 handleRunFailure 统一收口。
  2. 七个回调是扩展的全部缝隙：starting / environmentPrepared / contextPrepared / contextLoaded / started / ready / failed，EventPublishingRunListener 负责把它们翻成 ApplicationEvent。
  3. Web 类型推断看 classpath：Boot 4 改为 WebApplicationType.Deducer SPI（@since 4.0.1），WebFlux 侧由 WebFluxWebApplicationTypeDeducer 贡献。
  4. 失败三件套：handleRunFailure → FailureAnalyzer（内置 18 个，输出 Description/Action 结构）→ ExitCodeGenerators 汇总退出码；AbandonedRunException 是静默放弃短路。
  5. Startup 感知 CRaC：正常启动打 “Started”，检查点恢复打 “Restored”；native image 场景缺 JDK 25 会抛 NativeImageRequirementsException。

配置流： 6. ConfigDataEnvironmentPostProcessor 的 order 是 HIGHEST_PRECEDENCE+10，先于一切用户 EnvironmentPostProcessor 执行，保证后续的 spring.main.* 等绑定能看到文件配置。 7. 位置三通道：spring.config.import（显式导入）> additional-location（追加，默认位置仍生效）> location（整体替换默认）；默认为 classpath:/ 与 file:./、file:./config/。 8. Profile 两轮激活：先按当前激活集加载 application[-profile].{properties,yaml,yml}，再处理 spring.profiles.active/group/include 触发第二轮。 9. 优先级三条铁律：命令行参数 addFirst（最前）、ConfigData 产物 addLast（链尾）、DefaultPropertiesPropertySource 三处 moveToEnd（永远垫底）。 10. 松弛绑定的本质是 ConfigurationPropertyName 的元素类型（UNIFORM/DASHED/NON_UNIFORM）+ UNIFORM 规范化：server.port、SERVER_PORT、server-port 收敛到同一规范名。 11. @ConfigurationProperties 装配链：@EnableConfigurationProperties → EnableConfigurationPropertiesRegistrar → ConfigurationPropertiesBindingPostProcessor → ConfigurationPropertiesBinder → Binder。 12. 占位符解析在绑定之前：PropertySourcesPlaceholdersResolver 负责 ${...}，与 Binder 的类型转换接力完成；循环占位符快速失败，报错链带 Origin（来源文件 + 行号）。

自动配置： 13. 候选登记格式换代：Boot 4 用 META-INF/spring/%s.imports（ImportCandidates 读取），彻底告别 spring.factories 的 EnableAutoConfiguration 键。 14. AutoConfigurationImportSelector 五步漏斗：读候选 → 去重/排除过滤 → FilteringSpringBootCondition 双通道过滤 → AutoConfigurationSorter 排序 → 输出注册列表。 15. 双通道是保险丝：import 阶段的 AutoConfigurationImportFilter 与 refresh 阶段的 @Condition 结论必须一致，OnClassCondition 用线程池并行化类存在性检查。 16. 排序三段论：类名字母序打底 → @AutoConfiguration 的 order/before/after → 拓扑排序（检测到环直接抛异常，宁可启动失败）。 17. OnBeanCondition 的 REGISTER_BEAN 阶段只统计”将要注册”的 Bean 定义，自动配置之间不真正互相注入 Bean——这是顺序不敏感的根源；@ConditionalOnBean 写在用户代码里要警惕顺序。 18. 家底盘点：AutoConfiguration.imports 只有 12 个核心候选，全仓库 .imports 文件约 100 份——引入哪个 starter 决定你有哪些候选。

Web 流： 19. createWebServer 挂在 onRefresh：getWebServerFactory 要求容器内唯一的 ServletWebServerFactory Bean，多一个直接抛异常。 20. 两阶段分离是设计核心：initialize（bindOnInit=false，只建对象不绑端口）→ START_EVENT 之后 LifecycleProcessor 才调 webServer.start() 真正 bind——端口冲突报错发生在启动末端。 21. customizeConnector 是连接器配置收口点：协议、端口、SSL、HTTP2、ConnectorCustomizer 全在这里生效，源头是 ServerProperties 经 ServletWebServerFactoryCustomizer 回调。 22. 优雅停机链：server.shutdown=graceful → GracefulShutdown 挂进 Tomcat → WebServerGracefulShutdownLifecycle 在 GRACEFUL_SHUTDOWN_PHASE 等请求排空后才继续 stop。 23. Reactive 栈与 Servlet 栈接口同构：ReactiveWebServerApplicationContext + NettyReactiveWebServerFactory，读懂一边就能推另一边。

构建生态： 24. starter 零代码是特性：约定全在 build.gradle；Boot 4 再把容器拆成 compile/runtime 两个 starter（spring-boot-starter-tomcat-runtime，transitive=false），换容器不动编译期。 25. repackage 只做三件事：内容搬家（BOOT-INF/classes + BOOT-INF/lib/）、MANIFEST 改写（Main-Class=JarLauncher、Start-Class=原主类）、签名清理；原 jar 备份为 .original。 26. java -jar 的真实入口是 loader：Handlers.register() 注册 jar:nested: 协议 → LaunchedClassLoader 以嵌套 jar 为 classpath → 反射调 Start-Class；嵌套 jar 全程不解压。 27. 排障嵌套 jar 问题先查两件事：LaunchedClassLoader 可见性与 jar:nested: 协议是否注册（exploded 部署不走协议注册）。

端到端与排障： 28. 端到端①主线：java -jar → 协议注册 → loader 反射调 main → SpringApplication.run → onRefresh 建 Tomcat（initialize）→ START_EVENT → start 绑端口 → DispatcherServlet 接住第一个请求。 29. 端到端②主线：application.yml → ConfigDataEnvironmentPostProcessor → LocationResolver 解析位置 → Loader 读成 OriginTrackedMapPropertySource（addLast）→ Binder.bind → BindingPostProcessor 灌进 @ConfigurationProperties Bean。 30. --debug 打印条件评估报告（ConditionEvaluationReport），是排查”自动配置为什么没生效”的第一工具。 31. ApplicationRunner 与 CommandLineRunner 的区别：前者收 ApplicationArguments（解析过的选项/非选项参数），后者拿原始 String[]；callRunners 在 started 之后、ready 之前执行。 32. Banner、spring.banner.location、printBanner 都是 SpringApplication 自己的小事——启动期一切”环境相关行为”最终都能回溯到这个类。
