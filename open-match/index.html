〇、全景地图

先说人话：Open Match 是干什么的

多人游戏的服务器有两种：一种是”大厅服”，谁都能进；另一种是”对局服”，需要把水平相近、延迟可接受、模式一致的玩家凑成一桌，再给他们开一个专属的房间。

这个”凑一桌”的过程就叫 Matchmaking（匹配）。Open Match 做的事是：

  1. 每个等待匹配的玩家（或队伍）抽象成一张 Ticket（票），票上写着”我是什么段位 / 什么模式 / 我在哪个区”；
  2. 匹配器告诉 Open Match：“给我找出所有段位在 1500~1600、模式是 3v3 的票”（这叫 Pool / 池）；
  3. Open Match 把这些票喂给你写的 MMF（Match Making Function，匹配函数）；
  4. MMF 返回它认为合适的分组（Match），Open Match 把这些票从池里摘掉；
  5. 匹配器拿到 Match，去开房间，把连接信息给玩家。

v1 与 v2 的分水岭：v1 是”微服务全家桶”（frontend / backend / query / synchronizer / evaluator / swaggerui / scale 七个进程），框架深度参与”谁和谁配”的裁决；v2 把这些全砍了，只剩一个二进制 om-core，它的职责止于”编排 MMF 并把结果流式吐回来”——不再关心票是否被重复分配。

面试速通：Open Match 高频问题一页纸

高频 Q&A（先结论）

#问题结论
1Open Match v2 和 v1 最大的区别？v1 是微服务全家桶 + 框架裁决唯一性；v2 是单二进制 om-core + 不裁决。v2 删掉了 synchronizer 和 evaluator（docs/MIGRATION.md:45-49），MMF 的产物从”提案”变成”终局 match”。
2v2 还有哪些服务？只有一个 OpenMatchService，6 个 RPC：CreateTicket / DeactivateTickets / ActivateTickets / InvokeMatchmakingFunctions / CreateAssignments（废弃）/ WatchAssignments（废弃）（proto/api.proto:29-82）。
3Ticket ID 谁生成？存储层生成，就是 Redis Stream 的 entry ID。这是贯穿性不变式：replicatedticketcache.go:254 才回填 ticketPb.Id = curUpdate.Key。
4新创建的 Ticket 能立刻被匹配到吗？不能。 一律先进 InactiveSet（replicatedticketcache.go:257），必须 ActivateTickets 才进池。这保证”没成功复制并返回给客户端的票”永不被分配（main.go:176-182）。
5v2 用什么 Redis 数据结构？Streams。命令是 XADD / XREAD BLOCK / XTRIM MINID（redis.go:365/538/447）。没有 v1 的 sorted set 和 Lua 脚本。
6过滤器是 CEL 吗？不是。是自研的、基于 protobuf 字段的四类固定过滤器求交集：TagPresent / StringEquals / DoubleRange / CreationTimeRange（filter.go:52-139）。go.mod 里没有任何 CEL 依赖。
7一次能过滤多少票？gRPC 单消息 4MB 上限，OM 不调大它，而是把 participants 分块，每块带完整 Profile、只有票列表不同（main.go:670）。
8两个 MMF 返回了包含同一张票的 Match 会怎样？OM 完全不介入（“OM2 is no longer aware of ticket collisions”，docs/MIGRATION.md:49）。票会被 Deactivate 两次，冲突由开发者自己处理。
9Match 返回前要不要等票下线复制完成？默认要（OM_MATCH_TICKET_DEACTIVATION_WAIT=true，config.go:57）。关掉会更快但可能重复分配。
10Assignment 怎么给客户端？推荐 matchmaker 自己推。OM 的 CreateAssignments/WatchAssignments 都是 DEPRECATED（proto/api.proto:72-81）。
11WatchAssignments 是长轮询还是事件驱动？都不是——是 server-streaming 接口 + 内部每票一个 goroutine + time.Sleep(1s) 死循环轮询（main.go:1282-1298）。代码自己承认 naive（main.go:1318）。
12v2 怎么保证读性能？每个实例内存持有全量 ticket 副本，过滤/快照全走内存；Redis 只做复制总线。Redis 读端点还能挂只读副本横向扩展。
13v2 能删 Ticket 吗？没有删除 API。靠 TTL + deactivate 惰性清理（main.go:342-343 注释）。
14本地开发要起 Redis 吗？不用。OM_STATE_STORAGE_TYPE=memory 用内存复制器（main.go:143-151），但生产不推荐（main.go:150 有 WARN）。
15支持 Redis Cluster / 分片吗？明确不支持（docs/FAQ.md:42），假设单写实例。

易错点与面试坑

  1. 把 v1 的 FetchMatches / ReleaseTickets 套到 v2：v2 里这两个符号完全不存在（全仓库 grep 为 0）。等价物是 InvokeMatchmakingFunctions 与 ActivateTickets。
  2. 以为 Ticket 有 assignment 字段：v2 删掉了。Ticket 只有 id / expiration_time / attributes / extensions（proto/messages.proto:51-78），create_time 也下沉到了 attributes.creation_time。
  3. 以为过滤器支持表达式：只有四类固定语义，且字段缺失即淘汰（filter.go:90-93 的 !ok → return false）—— 这一点和 SQL 的 NULL 行为完全不同。
  4. 忽略 OM_CACHE_TICKET_TTL_MS 的 clamp 语义：客户端指定的 expiration_time 只能比默认更短，不能更长，否则 InvalidArgument（main.go:296-321）。
  5. 以为 DeactivateTickets 的部分失败会整体失败：不会。坏 ID 走 Status.details 的 BadRequest.FieldViolations 返回（main.go:1349-1367）。
  6. 以为 OM_MATCH_TICKET_DEACTIVATION_WAIT=true 就万无一失：源码明确承认无法等所有实例复制完成（main.go:1023-1029），这是最终一致性的固有限制。
  7. WatchAssignments 的性能：每票一个 goroutine + 1s 轮询，票多时 goroutine 数和 CPU 都是问题（这是它废弃的原因之一）。
  8. 以为 OM 会帮你去重：不会。要绕开自动 Deactivate，把候选放 Match.extensions 而不是 roster，由 Director 审批后自行 DeactivateTickets（docs/FAQ.md:80-86）。
  9. 用 == 比 time.Time：filter.go:79 / :84 就是这么写的。time.Time 是结构体，== 要求 wall + monotonic + *Location 三者全等；判相等一律用 .Equal()。上游 origin/misc-fixes（1bc2ae6）已修。
  10. 照着 TicketCount 这个指标做容量决策：replicatedticketcache.go:381 在删票分支里做了 numTickets++，导致清理过期票时存活计数反而 +1（:433 TicketCount = numTickets）。上游 60c9ddd 已删掉该行；在合入前请自行 patch 或改用 otel 侧别的口径。

第一讲：组件拓扑与进程模型 —— v2 到底砍了什么

第二讲：Ticket 生命周期 —— 从创建到激活

先说人话：本讲每个阶段在干什么

一张 Ticket 的一生只有四件事：被创建 →（必须）被激活 → 被某个 MMF 选中 → 被摘出池子。听起来简单，但 v2 在这条链上埋了三个反直觉的设计：

  1. Ticket 没有 ID 字段——ID 是存储层（Redis Stream）给的；
  2. 创建出来的票默认不参与匹配，必须显式激活；
  3. 没有”删除 Ticket”这个 API，票只会因为过期而消失。

这三个设计其实由同一个不变式串起来：Ticket ID ≡ Redis Stream entry ID。本讲会看到它如何同时决定了 ID 回填时机、初始 inactive、以及过期为什么能直接解析 ID 前 13 位当时间戳。

第三讲：状态存储抽象 —— Redis Streams 是唯一的真相

先说人话：本讲每个阶段在干什么

如果只能记住 v2 的一个技术决策，那就是：用 Redis Streams 当复制日志，而不是当数据库。

v1 把 Redis 当查询引擎（sorted set 索引 + Lua 脚本做过期扫描）；v2 把它当只追加的复制总线：写是 XADD 一条记录，读是 XREAD BLOCK 从游标往后拉，过期是 XTRIM MINID 按时间点裁掉。真正的”查询”发生在每个实例的内存里。

本讲先看接口有多薄（3 个方法），再看 Redis 实现怎么把四种操作映射成 stream fields，最后看 memory 实现为什么要刻意模仿 entry ID 的格式。

第五讲：过滤与匹配编排 —— InvokeMatchmakingFunctions 全景

先说人话：本讲每个阶段在干什么

这是全篇最长、也最有意思的一讲。一次匹配请求的完整流程是：

  1. 拿一份活跃票快照（不是实时查询）；
  2. 用四类过滤器把票分到各个 pool；
  3. 把 pool 打包成请求，超过 4MB 就切块；
  4. 并发调用你注册的所有 MMF（双向流）；
  5. MMF 每返回一个 Match，就把 Match 里的票摘出池子，并把 Match 流式推回调用方。

三个反直觉点：过滤器不是 CEL；MMF 不会被调用方断连取消；默认要等票下线复制完才把 Match 返回。

第六讲：Assignment 下发、配置与可观测性

先说人话：本讲每个阶段在干什么
