〇、全景地图

Java 21 的锁体系可以压缩成两大家族、三层骨架：

  • 家族一：synchronized 内置锁（JVM 层实现）——monitorenter/monitorexit 字节码 → ObjectSynchronizer::enter/exit → 轻量级快速路径 → ObjectMonitor 重量级慢路径。Object.wait/notify 直接操作 ObjectMonitor 的 _WaitSet 和 _cxq/_EntryList。
  • 家族二：JUC 显式锁（Java 层实现）——AbstractQueuedSynchronizer（AQS）提供 CLH 变种队列 + state int + Node{prev,next,waiter,status}，ReentrantLock/ReentrantReadWriteLock 继承 AQS，StampedLock 用独立的 CLH 变种（非 AQS 子类）。唤醒原语统一走 LockSupport.park/unpark。

三条主线：

  1. 加锁流：线程请求锁 → 快速路径 CAS（栈锁/BasicLock/LockStack）→ 失败则 inflate 到 ObjectMonitor（JVM 锁）或入 CLH 队列 park（JUC 锁）。
  2. 唤醒流：持锁线程释放 → exit/release → 从队列取后继 → unpark/LockSupport.unpark → 后继线程被唤醒后重新竞争。
  3. 锁升级流（仅 synchronized）：无锁（neutral mark）→ 轻量级锁（stack-locked 或 fast-locked）→ 重量级锁（inflated, ObjectMonitor）。无偏向锁阶段。

讲次主题核心文件一句话白话
第一讲synchronized 与锁升级objectMonitor.hpp/cpp、synchronizer.cpp、basicLock.hpp、lockStack.hppJVM 层的锁是一台”自动升降档”的变速箱：无竞争时用 mark word 里一个 bit 搞定，竞争一来自动膨胀成 ObjectMonitor（有 cxq 队列、有 park、有自旋）。JDK 21 把偏向锁砍了，只剩三档。
第二讲AQS 核心AbstractQueuedSynchronizer.javaAQS 是 JUC 锁的”底盘”：一个 volatile int state + 一条 CLH 变种双向链表 + acquire 里的一个大 for 循环。tryAcquire 交给子类写，入队/park/唤醒全在框架里包好。
第三讲ReentrantLockReentrantLock.javaReentrantLock 就是 AQS 穿了一件”可重入独占”的外套：state 当计数器、exclusiveOwnerThread 当持有者。公平和非公平只差一行——hasQueuedPredecessors。
第四讲读写锁ReentrantReadWriteLock.java、StampedLock.java把 state 劈成两半：高 16 位读、低 16 位写。StampedLock 更激进——用序号乐观读，读不加计数不 CAS，性能碾压但有”不可重入”的代价。
第五讲Condition 与 LockSupportConditionObject（AQS 内部）、LockSupport.java、AbstractOwnableSynchronizer.javaCondition 是”第二条等待队列”——await 时释放锁进 condition 队列，signal 时把节点搬到同步队列。LockSupport 的 permit 语义保证 unpark 先于 park 也有效。

高频 Q&A（先结论）

先答”一句话结论”列；被追问实现细节，按”深入”列回讲次。以下 16 题覆盖 Java 锁面试最高频问题，结论均提炼自各讲小结与源码分析。

#面试问题一句话结论深入
1synchronized 与 ReentrantLock 的区别？synchronized 是 JVM 层内置锁（monitorenter 字节码 → ObjectSynchronizer → ObjectMonitor），无竞争走 mark word 快速路径、竞争自动膨胀；ReentrantLock 是 Java 层 AQS 显式锁（volatile state + CLH 变种双向链表），需手动 lock/unlock，可选公平/非公平第一、三讲
2synchronized 锁升级过程？无锁 → 轻量级锁（LM_LEGACY 栈锁 / LM_LIGHTWEIGHT 快速锁）→ 重量级锁（inflate 成 ObjectMonitor）；竞争、wait、hash 都会触发膨胀第一讲
3JDK 21 还有偏向锁吗？没有。JDK 15 起偏向锁已移除，JDK 21 源码树 Biased 关键字零引用；答”无锁→偏向→轻量→重量”四段式已过时第一讲
4ObjectMonitor 有哪些队列？三条：_cxq（LIFO，CAS push 头部减少竞争）、_EntryList（FIFO 双向链表，exit 时从 cxq drain 而来）、_WaitSet（循环双链，wait/notify 专用）第一讲
5AQS 原理？一个 volatile int state + 一条 CLH 变种双向链表 + acquire 大循环：tryAcquire 交给子类，入队/park/唤醒全在框架里；release 后 signalNext 只唤醒一个后继第二讲
6公平锁与非公平锁的区别？只差一行：FairSync.tryAcquire 多一个 !hasQueuedPredecessors()；非公平可插队吞吐高，公平饿死低但上下文切换多。注意 tryLock() 始终非公平第三讲
7ReentrantLock 可重入原理？state 当重入计数、exclusiveOwnerThread 当持有者：owner==current 就 setState(c+1)，释放到 0 才清 owner第三讲
8lock() 与 lockInterruptibly() 的区别？lockInterruptibly 先查 Thread.interrupted()，再走 AQS 可中断版 acquireInterruptibly，等待期间可响应中断；lock() 入队 park 后不可中断第三讲
9读写锁的 state 如何拆分？int 劈两半：高 16 位读计数（CAS +SHARED_UNIT=65536）、低 16 位写计数；每线程读重入用 ThreadLocal，有 firstReader/cachedHoldCounter 两层优化第四讲
10写锁降级为何可行、读锁升级为何不可行？降级：先拿写锁再拿读锁再释放写锁；升级不行——tryAcquire 在 c!=0 && w==0（有读无写）时直接返回 false第四讲
11StampedLock 乐观读怎么工作？tryOptimisticRead 只读 state 序号，不加锁不 CAS；用完后 validate（loadFence + 序号比较）验证期间无写锁，失败或要写就升级为 readLock第四讲
12StampedLock 为什么不可重入？它不记录持有者，同线程重复 writeLock() 会 park 自己等待自己释放，直接死锁第四讲
13Condition 与 wait/notify 的区别？Condition 是挂在锁上的独立条件队列（firstWaiter/lastWaiter 单链表，可 new 多个）；wait/notify 只能用对象 monitor 的那条 _WaitSet第五讲
14Condition.await 会释放锁吗？会。await 调 enableWait 先 release(savedState) 释放全部重入计数，被 signal 唤醒后从条件队列迁到同步队列，再用保存的 state 重新竞争第五讲
15LockSupport 的 permit 语义？permit 不累积、至多一个；unpark 先于 park 也有效（permit 预存）；park 可能 spurious wakeup，必须 while 循环重检第五讲
16synchronized 的 wait/notify 为什么必须在同步块内？底层 ObjectMonitor::wait/notify 第一步都是 CHECK_OWNER，要求线程是该 monitor 的持有者；没进同步块就没有操作 _WaitSet 的身份第一讲

追问时的展开路线（按讲次）：

  • 第一讲：mark word 状态机与 LockingMode 三选项（LM_MONITOR 纯重量级 / LM_LEGACY 默认 / LM_LIGHTWEIGHT 实验性）→ inflate 按 mark 状态分情况处理（inflated / INFLATING / fast-locked / stack-locked / neutral）→ enter：CAS _owner → 重入检查 → TrySpin → EnterI（CAS push _cxq + park）； exit：drain _cxq→_EntryList → ExitEpilog unpark；wait：AddWaiter → exit → park → ReenterI；notify：DequeueWaiter → 移入 _cxq/_EntryList。
  • 第二讲：Node 的三个 status 常量（WAITING=1 / CANCELLED=0x80000000 / COND=2）与 ExclusiveNode/SharedNode 子类，ConditionNode 还实现 ManagedBlocker → acquire 是六参数方法（node, arg, shared, interruptible, timed, time），内部八步循环：检查队首 → tryAcquire → 初始化队列 → 创建节点 → casTail 入队 → 自旋 → 设 WAITING → park → release → signalNext 只唤醒 head.next（共享模式用 signalNextIfShared）； hasQueuedPredecessors 是公平锁基石，apparentlyFirstQueuedIsExclusive 用于非公平读写锁防写者饥饿。
  • 第三讲：Sync extends AQS，state 当重入计数、exclusiveOwnerThread 当持有者 → lock() 先 initialTryLock 快速路径再 acquire(1)；tryAcquire 的公平差异只有 !hasQueuedPredecessors() 一行 → tryRelease 用 setState(c) 普通 volatile 写不用 CAS（只有持锁线程能调，无竞争）； exclusiveOwnerThread 非 volatile，靠 state 的 volatile 读写保证 happens-before。
  • 第四讲：SHARED_SHIFT=16 把 state 劈成两半，读锁 CAS 加 SHARED_UNIT=65536（进位到高位），写锁 CAS 加 1 → 写锁走 tryAcquire（c==0 才 CAS），读锁走 tryAcquireShared（返回 int，>=0 成功，失败 -1 转 fullTryAcquireShared）→ 每线程读重入用 ThreadLocal，配 firstReader/cachedHoldCounter 两层优化；写锁降级可行、读锁升级不可行 → StampedLock 不继承 AQS，用 64 位 state（bit7 写锁 / 低 7 位读计数 / 高位序号）做乐观读，三种模式按 stamp 区分。
  • 第五讲：await 五步全流程（创建 ConditionNode → enableWait 释放锁并入条件队列 → park → canReacquire 为真 → acquire(savedState) 恢复重入计数）→ signal → doSignal → enqueue 把节点迁到同步队列（只移一个，signalAll 全移）→ permit 三特性（不累积 / unpark 可先行 / spurious wakeup 要循环）； 虚拟线程走 VirtualThreads.park/unpark，不阻塞载体线程。

易错点与面试坑

  • 坑 1：版本差异（最高频翻车点）。JDK 15 起偏向锁已移除，JDK 21 源码树 Biased 关键字零引用，升级路径只剩”无锁 → 轻量级 → 重量级”三段；背诵四段式属于过期答案。
    • 追问就补：LockingMode 默认 LM_LEGACY（BasicLock displaced header），另有 LM_MONITOR 纯重量级与实验性 LM_LIGHTWEIGHT（LockStack 快速锁）。
    • 加分项：INFLATING 中间态只有 LM_LEGACY 有；LM_LIGHTWEIGHT 的轻量级只有 fast-locked 一档。
  • 坑 2：tryLock() 永远非公平。Sync.tryLock 不检查队列直接 CAS，即使在 FairSync 模式下也不排队——公平性只在 lock() 路径上成立。
    • 追问就补：lock() 入口先试 initialTryLock；FairSync 的实现会先查 hasQueuedThreads，NonfairSync 的直接 CAS。
    • 加分项：public tryLock() 转调的就是 Sync.tryLock，所以”公平锁的 tryLock”这个组合不存在。
  • 坑 3：lock() 不能响应中断。等待期间要响应中断必须用 lockInterruptibly()（走 AQS 可中断路径）；lock() 一旦入队 park 就发现不了中断。
    • 追问就补：lockInterruptibly 进 AQS 前先查 Thread.interrupted()，再走可中断版 acquireInterruptibly。
    • 加分项：tryLock(timeout, unit) 走 tryLockNanos，既可中断又有超时，同样先试 initialTryLock。
  • 坑 4：Condition.await 是”先放锁再等”。await 会 release(savedState) 释放全部重入计数；醒来后不是继续持锁，而是带保存的 state 重新竞争锁。
    • 追问就补：enableWait 把节点挂上条件队列后才 release；返回路径用保存的 savedState 恢复重入计数。
    • 加分项：signal 只把头节点从条件队列 enqueue 到同步队列，要全喊必须 signalAll。
  • 坑 5：两条队列结构不同，别搞混。同步队列是 head/tail 双向链表（Node 有 prev/next），Condition 条件队列是 firstWaiter/lastWaiter 单链表；节点被 signal 后才”迁移”进同步队列。
    • 追问就补：JDK 21 的 Node 用 status（WAITING / CANCELLED / COND 三个常量）加 ExclusiveNode/SharedNode 子类区分模式，不再有 SIGNAL/PROPAGATE。
    • 加分项：canReacquire 通过 node.prev 是否为 null 判断节点是否已被搬进同步队列。
  • 坑 6：乐观读 validate 通过 ≠ 万事大吉。validate 只证明”读的瞬间序号没变”；之后要做写操作必须升级成 readLock，否则数据可能已经坏了。
    • 追问就补：validate 用 loadFence 保证读操作不被重排到验证之前，再比较序号是否变化。
    • 加分项：StampedLock 不可重入——不记录持有者，同线程重复 writeLock() 会 park 自己等自己释放，直接死锁。
  • 坑 7：读锁不能升级写锁，写锁可以降级。c!=0 && w==0 时 tryAcquire 直接返回 false；正确姿势是”先拿写锁 → 再拿读锁 → 释放写锁”完成降级。
    • 追问就补：降级顺序不能反——文档给出的标准姿势是先 readLock().lock()（写锁持有者可以获取读锁），再 writeLock().unlock()。
    • 加分项：非公平读锁靠 apparentlyFirstQueuedIsExclusive 只在队首是写者时阻塞新读者，是概率性防写者饥饿，不保证写者不饿死。
  • 坑 8：park 可能无理由返回（spurious wakeup）。park 必须包在 while (!canProceed) { park(); } 循环里重检条件；unpark 先于 park 也有效（permit 预存），但 permit 不累积、至多一个。
    • 追问就补：permit 语义下多次 unpark 等于一次，这是 LockSupport 与 Semaphore 计数许可的区别。
    • 加分项：虚拟线程的 park/unpark 走 VirtualThreads，不阻塞载体线程；ConditionNode 实现 ForkJoinPool.ManagedBlocker，在 ForkJoinPool 里 await 不占线程。

第一讲：synchronized 与锁升级 —— ObjectMonitor 与 ObjectSynchronizer

先说人话：本讲每个阶段在干什么

类比：synchronized 就像一栋办公楼的门禁系统。一个人进来（加锁），门禁先看有没有门禁卡（mark word 的 CAS 快速路径），有的话直接放行，不费吹灰之力。如果两个人同时刷卡（竞争），门禁系统就要升级——请出保安（ObjectMonitor），发号牌（入队），在门口等（park）。等前面的人出来（exit），保安呼叫下一个号（unpark），下一个人进门。

阶段干了什么为什么
快速路径（fast path）CAS 操作 mark word，成功直接返回99% 的锁无竞争，不值得进入重量级队列
膨胀（inflate）创建 ObjectMonitor，CAS 安装到 mark word轻量级搞不定了（竞争/wait/hash），需要完整的队列和 park 机制
重量级 enterCAS _owner、TrySpin、EnterI（入 cxq + park）让竞争失败的线程有序排队、不忙等浪费 CPU
重量级 exit释放 _owner、drain cxq→EntryList、ExitEpilog(unpark)让等待的后继线程被唤醒
wait/notifyAddWaiter 进 _WaitSet、exit 释放锁、park；notify 从 _WaitSet 移到 _cxq实现 Object.wait/notify 语义，需要第二条等待队列

本讲主线：mark word 的状态机 + ObjectMonitor 的 cxq/EntryList/WaitSet 三条队列 + enter/exit/wait/notify 四个操作如何操纵这些队列。

1.1 mark word 与锁状态

JDK 21 的 mark word 定义在 oops/markWord.hpp（本源码树 oops/ 目录缺失，但可通过 objectMonitor.hpp:30 的 #include "oops/markWord.hpp" 和 synchronizer.cpp 的使用推断其布局）。

LM_LEGACY 模式（默认，globals.hpp:1973）的 mark word 布局（64 位）：

| unused:1 | lock-bias:2 | hashcode:31 | age:4 | 0 →  无锁 (neutral)
| pointer_to_BasicLock:62             | 00 →  栈锁 (stack-locked/has_locker)
| 0:64                                  →  INFLATING (膨胀中, 仅 LM_LEGACY)
| pointer_to_ObjectMonitor:62         | 10 →  重量级锁 (inflated/has_monitor)

LM_LIGHTWEIGHT 模式（实验性，globals.hpp:1977）：

| hashcode:31 | age:4 | 0 →  无锁 (neutral, is_neutral)
| 0:62                         | 1 →  快速锁 (fast-locked, is_fast_locked)

  • mark.has_monitor() — 重量级锁，mark 指向 ObjectMonitor

1.5 ObjectMonitor::enter —— 重量级加锁

objectMonitor.cpp:324 的 enter() 按”最快路径优先”排列：

enter() (objectMonitor.cpp:324)
  ├── CAS _owner null→current (328)        成功 → return true
  ├── _owner == current (334)              重入 → _recursions++; return true
  ├── _owner 指向自己的 BasicLock (340)    LM_LEGACY 重入 → _recursions=1; 转换 owner
  ├── TrySpin(current) (356)              自旋 → 成功 return true
  └── EnterI(current) (686)                入队 + park 循环

EnterI（objectMonitor.cpp:686）核心逻辑：

// 先 TryLock (690) 和取消 deflation (697)
ObjectWaiter node(current);                    // 745
node.TState = ObjectWaiter::TS_CXQ;            // 748
// CAS push 到 _cxq 头部
for (;;) {
    node._next = nxt = _cxq;                  // 756
    if (Atomic::cmpxchg(&_cxq, nxt, &node) == nxt) break;  // 757
    if (TryLock(current) > 0) return;          // 761: CAS 失败顺便试锁
}
// 成为 Responsible 线程 (792-796)
if (nxt == nullptr && _EntryList == nullptr)
    Atomic::replace_if_null(&_Responsible, current);
// park 循环 (812-827)
for (;;) {
    if (TryLock(current) > 0) break;
    if (_Responsible == current)
        current->_ParkEvent->park(recheckInterval);  // 819: 定时 park
    else
        current->_ParkEvent->park();                 // 826: 无限 park
    if (TryLock(current) > 0) break;
}

关键设计：

  1. cxq LIFO：新来线程 CAS 到 cxq 头部（objectMonitor.cpp:756-757），减少 CAS 竞争。
  2. Responsible 线程：至多一个线程用定时 park（objectMonitor.cpp:818-827），防止”搁浅”（stranding）——所有线程 park 了但锁是空闲的。
  3. TrySpin 先行：入队前先自旋（objectMonitor.cpp:356, 724），如果锁持有时间极短可避免入队开销。

第二讲：AQS 核心 —— AbstractQueuedSynchronizer

先说人话：本讲每个阶段在干什么

类比：AQS 是一个”取号排队机”。线程来取号（tryAcquire），如果成功直接走人；如果失败，拿到一个号牌（Node），排进队伍（CLH 队列），然后坐下来等（park）。前面的人办完事（release），按一下叫号器（signalNext → unpark），下一个人站起来再去试（被唤醒后重新 tryAcquire）。

  2. 队首时 tryAcquire/tryAcquireShared（拿到锁就设 head 并返回）
  3. 队列为空时初始化 head（tryInitializeHead，AbstractQueuedSynchronizer.java:582）
  4. 第一次进循环时创建 Node（SharedNode 或 ExclusiveNode）
  5. CAS 入队（casTail，AbstractQueuedSynchronizer.java:738-744）

先说人话：本讲每个阶段在干什么

    return (stamp & SBITS) == (state & SBITS);  // 640: 序号没变 = 乐观读有效
}

关键：U.loadFence() 确保读操作在 validate 之后执行。如果 stamp 没变（没有写锁释放），乐观读期间的数据是一致的。

public long writeLock() {                       // 473
    long s = U.getLongOpaque(this, STATE) & ~ABITS, nextState;
    if (casState(s, nextState = s | WBIT)) {    // 476: CAS 设写锁位

}

public long readLock() {                        // 548

    if (casState(s, nextState = s + RUNIT))      // 551: CAS 读计数 +1

第五讲：Condition 与 LockSupport —— 等待与唤醒的底层

先说人话：本讲每个阶段在干什么

类比：Condition 是锁旁边的”第二条队伍”。正常排队（同步队列）的人在等锁；Condition 队列的人在等一个信号。await = 释放锁 → 进第二条队伍 → park → 被 signal 唤醒 → 搬回第一条队伍 → 重新排队拿锁。LockSupport 是最底层的”门铃”——unpark 按一下门铃，下次 park 立刻开门，先按后等也有效。

5.2 await —— 等待

AbstractQueuedSynchronizer.java:1689-1726：

public final void await() throws InterruptedException {
    if (Thread.interrupted())
        throw new InterruptedException();         // 1690-1691
    ConditionNode node = newConditionNode();      // 1692: 创建节点
    if (node == null) return;
    int savedState = enableWait(node);            // 1695: 释放锁 + 入条件队列
    LockSupport.setCurrentBlocker(this);          // 1696: 设 blocker 用于诊断
    boolean interrupted = false, cancelled = false, rejected = false;
    while (!canReacquire(node)) {                 // 1698: 还在条件队列就继续等
        if (interrupted |= Thread.interrupted()) {
            if (cancelled = (node.getAndUnsetStatus(COND) & COND) != 0)
                break;                             // 1700-1701: 被中断且 COND 还在 → 取消
        } else if ((node.status & COND) != 0) {   // 1702: 仍在条件队列
            try {
                if (rejected)
                    node.block();                 // 1705: 直接 block
                else
                    ForkJoinPool.managedBlock(node);  // 1707: ForkJoinPool 兼容
            } catch (RejectedExecutionException ex) {
                rejected = true;                   // 1708
            } catch (InterruptedException ie) {
                interrupted = true;                 // 1710
            }
        } else
            Thread.onSpinWait();                  // 1714: 刚被 enqueue, 自旋等
    }
    LockSupport.setCurrentBlocker(null);          // 1716: 清 blocker
    node.clearStatus();                            // 1717: 清状态
    acquire(node, savedState, false, false, false, 0L);  // 1718: 重新获取锁
    if (interrupted) {
        if (cancelled) {
            unlinkCancelledWaiters(node);         // 1721
            throw new InterruptedException();      // 1722
        }
        Thread.currentThread().interrupt();       // 1724
    }
}

enableWait（AbstractQueuedSynchronizer.java:1559-1575）——入条件队列 + 释放锁：

private int enableWait(ConditionNode node) {
    if (isHeldExclusively()) {
        node.waiter = Thread.currentThread();
        node.setStatusRelaxed(COND | WAITING);    // 1562: 设 COND+WAITING
        ConditionNode last = lastWaiter;
        if (last == null)
            firstWaiter = node;                   // 1565: 第一个
        else
            last.nextWaiter = node;               // 1567: 追加到尾部
        lastWaiter = node;
        int savedState = getState();
        if (release(savedState))                  // 1570: 释放锁! 返回保存的 state
            return savedState;
    }
    node.status = CANCELLED;
    throw new IllegalMonitorStateException();      // 1574: 没持锁
}

canReacquire（AbstractQueuedSynchronizer.java:1583-1588）——判断节点是否已被转移到同步队列：

private boolean canReacquire(ConditionNode node) {
    Node p;
    return node != null && (p = node.prev) != null &&  // 586: 有 prev = 已在同步队列
        (p.next == node || isEnqueued(node));
}

await 全流程：

  1. 创建 ConditionNode
  2. enableWait：设 COND|WAITING → 加到条件队列尾部 → release(savedState) 释放锁
  3. while (!canReacquire)：在条件队列时 ForkJoinPool.managedBlock 或 node.block() park
  4. 被 signal 唤醒后 canReacquire 返回 true（节点已入同步队列）
  5. acquire(node, savedState, ...)：重新竞争锁（用保存的 state 恢复重入计数）

private void doSignal(ConditionNode first, boolean all) {
    while (first != null) {
        ConditionNode next = first.nextWaiter;
        if ((firstWaiter = next) == null)
            lastWaiter = null;                      // 1510: 队列空了
        if ((first.getAndUnsetStatus(COND) & COND) != 0) {

        first = next;

enqueue（AbstractQueuedSynchronizer.java:606-625）——把 ConditionNode CAS 到同步队列 tail：

final void enqueue(ConditionNode node) {
    if (node != null) {
        boolean unpark = false;
        for (Node t;;) {
            if ((t = tail) == null && (t = tryInitializeHead()) == null) {
                unpark = true;                     // 611: OOME, 唤醒自旋
                break;
            }
            node.setPrevRelaxed(t);
            if (casTail(t, node)) {                // 615: CAS 入同步队列
                t.next = node;
                if (t.status < 0)                  // 617: 前驱 CANCELLED
                    unpark = true;                 // 唤醒清理
                break;
            }
        }
        if (unpark)
            LockSupport.unpark(node.waiter);       // 623
    }
}

signal 全流程：

  1. 检查 isHeldExclusively（必须持锁）
  2. doSignal：从条件队列取头节点
  3. getAndUnsetStatus(COND)：清除 COND 位（标记”已转移”）
  4. enqueue：CAS 到同步队列 tail
  5. 被转移的节点在同步队列里走正常 acquire 流程

5.4 LockSupport —— 底层阻塞原语

LockSupport.java:140 定义了 park/unpark 原语：

permit 语义

LockSupport.java:45-51 的 Javadoc：

This class associates, with each thread that uses it, a permit (in the sense of the Semaphore class). A call to park will return immediately if the permit is available, consuming it in the process; otherwise it may block. A call to unpark makes the permit available, if it was not already available. (Unlike with Semaphores though, permits do not accumulate. There is at most one.)

关键特性：

  1. permit 不累积——至多一个
  2. unpark 先于 park 也有效——permit 被记录
  3. park 可能”无理由”返回（spurious wakeup），必须在循环中重检条件

synchronized 与锁升级： 1. JDK 21 已彻底移除偏向锁，runtime/ 目录下 Biased 关键字零引用（globals.hpp 无 BiasedLocking 产品标志）。锁升级路径：无锁 → 轻量级锁（stack-locked 或 fast-locked）→ 重量级锁（inflated/ObjectMonitor），三段式。 2. LockingMode 默认 LM_LEGACY（1），可选 LM_MONITOR（0，纯重量级）和 LM_LIGHTWEIGHT（2，实验性新轻量级，用 LockStack 替代 BasicLock displaced header）（globals.hpp:1973-1978）。 3. ObjectMonitor 有三条队列：_cxq（LIFO CAS 入队）、_EntryList（FIFO 双向链表，exit 时从 cxq drain 过来）、_WaitSet（循环双向链表，wait/notify 用）（objectMonitor.hpp:173,177,189）。 4. ObjectMonitor::enter（objectMonitor.cpp:324）顺序：CAS _owner → 重入检查 → TrySpin → EnterI（CAS push _cxq + park）。_succ（objectMonitor.hpp:178）和 _Responsible（objectMonitor.hpp:179）是防搁浅双保险。 5. ObjectMonitor::exit（objectMonitor.cpp:1141）：release_clear_owner → storeload → drain _cxq→EntryList → ExitEpilog（unpark 后继）。_cxq 到 EntryList 的 drain 是 LIFO→FIFO 转换（objectMonitor.cpp:1268-1301）。 6. Object.wait 调 ObjectMonitor::wait（objectMonitor.cpp:1440）：AddWaiter 入 _WaitSet → exit 释放锁 → park → 醒后 DequeueSpecificWaiter → ReenterI 或 enter 重新竞争。notify 调 INotify（objectMonitor.cpp:1662），从 _WaitSet 取头节点 prepend 到 _cxq 或直接入 _EntryList。 7. inflate（synchronizer.cpp:1314）处理四种 mark 状态：inflated（直接返回）、INFLATING（仅 LM_LEGACY，自旋等待）、fast-locked（LM_LIGHTWEIGHT，新建 OM + CAS）、stack-locked（LM_LEGACY，INFLATING 中间态 + CAS）、neutral（新建 OM + CAS）。

AQS 核心： 8. JDK 21 的 Node（AbstractQueuedSynchronizer.java:467-499）大改：status 替代 waitStatus，只有 WAITING=1、CANCELLED=0x80000000、COND=2 三个常量（AbstractQueuedSynchronizer.java:462-464），不再有 SIGNAL/PROPAGATE。模式从常量改为子类 ExclusiveNode/SharedNode（AbstractQueuedSynchronizer.java:502-503）。 9. acquire(node, arg, shared, interruptible, timed, time)（AbstractQueuedSynchronizer.java:670）是合并了独占/共享/可中断/超时的 6 参数方法，取代了旧版分散的 acquireQueued/doAcquireSharedNanos 等。8 步循环：检查队首 → tryAcquire → 初始化队列 → 创建节点 → casTail 入队 → 自旋 → 设 WAITING → park。 10. signalNext（AbstractQueuedSynchronizer.java:641-647）只唤醒 head.next 一个后继，清 WAITING 位 + unpark。共享模式有 signalNextIfShared（AbstractQueuedSynchronizer.java:650-657）只唤醒 SharedNode。 11. hasQueuedPredecessors（AbstractQueuedSynchronizer.java:1284-1291）是公平锁的基石——返回 true 表示有前驱应等待。apparentlyFirstQueuedIsExclusive（AbstractQueuedSynchronizer.java:1235-1239）检查队首是否是写者，用于非公平读写锁的防写者饥饿。 12. ConditionNode（AbstractQueuedSynchronizer.java:505-522）实现了 ForkJoinPool.ManagedBlocker，在 ForkJoinPool 中 await 不会阻塞线程池。

ReentrantLock： 13. 公平与非公平的差别只有一行：FairSync.tryAcquire（ReentrantLock.java:280）比 NonfairSync.tryAcquire（ReentrantLock.java:242）多了 !hasQueuedPredecessors()。 14. tryLock()（ReentrantLock.java:125-140）始终非公平——不检查队列直接 CAS，即使在 FairSync 模式下。public tryLock()（ReentrantLock.java:401）调的就是它。 15. tryRelease（ReentrantLock.java:172-181）不用 CAS——只有持有锁的线程才调 tryRelease，无竞争。exclusiveOwnerThread 非 volatile（AbstractOwnableSynchronizer.java:64），靠 state 的 volatile 读写保证 happens-before。 16. initialTryLock（ReentrantLock.java:148）是抽象方法，在 lock() 进入 AQS 队列前先试快速路径。NonfairSync 直接 CAS（ReentrantLock.java:225），FairSync 先检查 hasQueuedThreads（ReentrantLock.java:263）。

读写锁： 17. ReentrantReadWriteLock 的 state 高 16 位是读计数、低 16 位是写计数（ReentrantReadWriteLock.java:263-271）。SHARED_UNIT=65536（ReentrantReadWriteLock.java:264）用于 CAS 高位 +1。 18. 每线程读重入用 ThreadLocal<HoldCounter>（ReentrantReadWriteLock.java:299），有 firstReader（ReentrantReadWriteLock.java:335）和 cachedHoldCounter（ReentrantReadWriteLock.java:315）两层优化。 19. 写锁降级可行（先写锁再读锁再释放写锁），读锁升级到写锁不可行（tryAcquire 在 c!=0 && w==0 时返回 false，ReentrantReadWriteLock.java:399）。 20. NonfairSync.readerShouldBlock 调 apparentlyFirstQueuedIsExclusive（ReentrantReadWriteLock.java:693）——只在队首是写者时阻塞新读者，防写者饥饿的启发式策略。FairSync 的读写都调 hasQueuedPredecessors（ReentrantReadWriteLock.java:703-706）。 21. StampedLock（StampedLock.java:242）不继承 AQS，用 64 位 state：bit7=写锁、bit0-6=读计数、高位=序号。tryOptimisticRead（StampedLock.java:621）只读 state 不 CAS，validate（StampedLock.java:638）用 loadFence + 序号比较。StampedLock 不可重入。

Condition 与 LockSupport： 22. ConditionObject（AbstractQueuedSynchronizer.java:1483）用 firstWaiter/lastWaiter 单链表管理条件队列，与同步队列的双向链表不同。await（AbstractQueuedSynchronizer.java:1689）调 enableWait（AbstractQueuedSynchronizer.java:1559）释放锁入条件队列。 23. signal（AbstractQueuedSynchronizer.java:1528）调 doSignal（AbstractQueuedSynchronizer.java:1506）把节点 enqueue（AbstractQueuedSynchronizer.java:606）到同步队列 tail，从条件队列转移到同步队列。 24. LockSupport permit 不累积，至多一个。unpark 先于 park 也有效。park 可能 spurious wakeup，必须在循环中使用。 25. LockSupport 对虚拟线程透明：park 检查 isVirtual 走 VirtualThreads.park（LockSupport.java:218-222），unpark 走 VirtualThreads.unpark（LockSupport.java:178-183）。 26. AbstractOwnableSynchronizer（AbstractOwnableSynchronizer.java:50）只有一个 exclusiveOwnerThread 字段（AbstractOwnableSynchronizer.java:64），非 volatile，靠 state 的 volatile 保证 happens-before。
